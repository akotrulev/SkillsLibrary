# doc-business-model evals

Regression evals for `dev:doc-business-model`, run through `be-feature-documenter` (eval 1) and `be-documenter` in FULL mode (eval 2 — the fixture has no knowledge base, so a run on it is FULL by definition; the prompt pre-confirms the scope and the one-area split). Eval 3 runs `be-documenter` with a two-session split confirmed, so it must write a runnable plan and stop.

- `fixture/` — a small .NET 8 minimal-API / EF Core codebase for the workshop-booking credits domain: plans (Basic 8 credits at £6.00, Plus 16 credits at £5.00), tiers 1/2/3, booking and cancellation endpoints, the 24-hour late-cancel rule, monthly posting, at-least-once pricing. It is the **only** source for these evals. The golden examples (`../references/example-*.md`) describe the same domain over an imagined codebase and deliberately differ from the fixture in several facts.
- `evals.json` — the two prompts and their rule-based expectations (skill-creator format). Expectations are never line-exact.

This README sits outside `fixture/`, so the agent under test never sees it.

## What is tested

- The three level files exist (Level 3 may add `<name>.technical.<topic>.md` splits, nothing else); `doc-lint.py` passes.
- Level 1: exact numbers, a worked example whose overage arithmetic uses fixture values and is correct, client vocabulary, the quoted refusal text, no code nouns.
- No `#confirmed` in the three level files; Levels 1–2 avoid the skill's judging words (bug, defect, flaw, broken, wrong, mistake, vulnerability, "should have"); defects (the fixture has some, deliberately not listed here) are reported as Level 3 Findings only.
- Same commit sha in every stamp line (`Derived from …` for the KB, `Generated by … @ <commit>` for features) and an Audience line on each file.
- **Golden-copy detectors.** The expectations prefixed `Golden-copy check:` hold only for a document traced from the fixture and fail for one copied from the goldens: cancellation returns retried 3× then parked, the 5-second pickup, fixed tier costs, no way to set a personal overage rate, the monthly reset running before the save, real fixture paths in Level 3, and the Plus plan.
- Eval 2 only: the system-overview set (three files) exists, and `INDEX.md` has one line for the credits area naming its three files. The run also writes flows, entities, decisions, events, glossary and active-context; those are not graded individually.
- Eval 3 only: one plan in `docs/plans/` in the library's plan format (`engineering-practices/writing-plans/references/plan-format.md`, shaped by `backend/_shared/codebase-survey/references/documentation-plan.md`) — tasks A1, A2 and K1 in sequence, machine-readable prompt headings and first lines, the close-out section — and no area documented in the survey session.

## How to run

```bash
W=$(mktemp -d) && cp -R fixture/. "$W" && cd "$W"
git init -q && git add -A && git commit -qm "fixture"
```

Open Claude Code in `$W` with the plugins enabled — eval 1: `dev` and `be-dotnet`; eval 2: `dev`, `be-dotnet` and `business-analysis` (`be-documenter` uses its knowledge-base skills) — then:

- eval 1: `/dev:document-feature Document the credit pricing and overage charges feature of the fixture`
- eval 2: `/dev:document-system` with the eval 2 prompt from `evals.json` (scope and split pre-confirmed, so the survey gate does not stop)
- eval 3: `/dev:document-system` with the eval 3 prompt (same plugins as eval 2); it ends at the written plan — do not run the plan's prompts

Then lint and check each expectation by hand or with a grader:

```bash
python3 <library>/backend/_shared/business-documentation/scripts/doc-lint.py --dir docs/features        # eval 1
python3 <library>/backend/_shared/business-documentation/scripts/doc-lint.py --dir docs/business-model  # eval 2
```

Eval 3 has nothing to lint: read `docs/plans/*.md` against its expectations.

## When an expectation fails

Fix the skill or agent, not the expectation. A failed `Golden-copy check` means the agent took facts from a golden example instead of tracing the fixture — fix the instruction that let it, never the expectation or the fixture. For any other expectation that contradicts a golden example in shape or tone, fix whichever of the two is wrong and say why in the commit.

Goldens are illustrations, never sources; where they differ from the fixture in any fact or wording (retries, timing, tier configuration, plans, paths, the plan-name refusal text), the fixture wins.
