# Skills Library — full catalog

> **This is the reference inventory for the SkillsLibrary.** It describes every folder, skill, agent, and published plugin, and how they route to each other. It is *not* auto-loaded into every session — the behavioral rules every skill follows live in [`../CLAUDE.md`](../CLAUDE.md); this file is the map you consult when you need to know what exists and which agent owns it.

## Scope & published plugins

## Slash-command surface (per plugin)

Never add a command for one without saying why the agent path is insufficient.

## QA skills catalog

The `qa/` folder is the most built-out section. When a request matches one of these, prefer the matching skill over improvising. The folder is organized **stack-first** so a new project copies one stack folder plus the agnostic ones, and **domain-encapsulated**: each top-level folder owns a domain, and *its skills are loaded only by its own agents*. Stack agents author + verify; test design (`qa/manual/`), reporting (`qa/reporting/`), CI/CD (`qa/cicd/`), and security (`qa/_shared/agents/qa-security`) are **peer agents** the orchestrator (you, or the human) invokes alongside the stack agent — a stack agent never reaches into another folder's skills.

- `qa/{java,dotnet,typescript}/skills/{node}/SKILL.md` — the per-stack skill implementations (C# → `dotnet/`); pick the stack from the Stack defaults above or the user's project. Tool-bound skills exist only under the stack(s) the tool supports (e.g. `performance/nbomber` only in `dotnet/`). One-of-N tool families (messaging, email, network-mocking, visual-regression, accessibility, file-storage) are **one registered skill per family**: SKILL.md routes via a decision matrix, the per-tool deep dive lives in `references/<tool>.md`. Oversized skills keep their deep sections in `references/details.md`.
- `qa/{java,dotnet,typescript}/agents/` — numbered orchestrator agents for that stack (senior automation QA per focus: api / ui / mobile / performance / llm / bdd); they load **only the stack's own skills** (foundations → author → deep verification → review), and name the manual / reporting / cicd / security agents as related peers to run separately. The **`qa-llm-{stack}`** agent owns LLM-app eval suites end-to-end (choose spine → build dataset → author property/rubric/grounding assertions → stochastic pass-rate + red-team → review) and loads `ai-feature-testing` (+ `data-driven-testing`, `api-models`, `test-login-tokens`).
- The **`qa-bdd-{stack}`** agent owns Gherkin/BDD **living-documentation** UI suites (web + mobile) end-to-end: **consume** a `qa-test-case-designer` test-case suite → canonicalize steps into reusable declarative `.feature` files (Background, Scenario Outline, tags) → generate step definitions split by domain → implement each step against **existing page objects** → review. It loads the cross-stack `qa/_shared/bdd/feature-file-writer` plus its stack's `bdd-project-setup` / `gherkin-step-code` / `bdd-reviewer` and the stack's page-object/ui skills; the BDD framework is per stack — **Reqnroll** (dotnet) · **Cucumber-JVM** (java) · **playwright-bdd** web + **CucumberJS+WebdriverIO** mobile (typescript). Names `qa-test-case-designer` (test cases), `qa-ui-{stack}` / `qa-mobile-{stack}` (page objects), `qa-reporting-{stack}`, `qa-cicd-{stack}` as peers.
- `qa/manual/` — language-agnostic process skills: `requirements-breakdown`, `test-case-writer`, `test-plan-writer`, `test-design-techniques`, `bug-report-writer`, `exploratory-charter-writer`, `test-strategy`, `quality-metrics`; loaded only by the two `qa/manual/agents/` — `qa-test-case-designer`, the step-by-step agent that turns documentation into a full manual test-case suite, and `qa-test-planner`, the step-by-step agent that turns a feature (documented or not) into a saved test plan in `docs/test-plans/` — scope in/out, harness looked up from the repo, artifacts, and a case inventory gap-analyzed (`existing`/`extend`/`new`) against the automation that already exists.
- `qa/reporting/{java,dotnet,typescript}/skills/` — `test-reports` (Allure results) + `flaky-test-quarantine` (tag/quarantine tests by finding); per-stack agents `qa/reporting/agents/qa-reporting-{java,dotnet,typescript}` wire Allure, tag tests, and detect/quarantine flakes.
- `qa/cicd/` — `ci-pipelines` per stack (`qa/cicd/{java,dotnet,typescript}/skills/ci-pipelines`, a one-of-N family routing to `references/<host>.md`: github-actions · azure-pipelines · gitlab-ci) + the language-agnostic `qa/cicd/ci-conventions`; per-stack agents `qa/cicd/agents/qa-cicd-{java,dotnet,typescript}` build the pipeline (shard matrix, Allure-publish step, perf gate, OIDC secrets).
- `qa/_shared/` — cross-stack technical rules referenced by stack skills (`api-contract-testing`, `api-spec-assets`, `performance`, `security` + the language-agnostic `security-testing/*` scanner skills, and `bdd/feature-file-writer` — the framework-agnostic Gherkin engine loaded by every `qa-bdd-{stack}` agent) plus `qa-python-web-testing` (the one Python skill, Anthropic-provided import); also `qa/_shared/agents/qa-security` — the cross-stack, OWASP-mapped security orchestrator (loads the `_shared` scanner skills + the project's stack-native security siblings, incl. `dependency-scan`, step by step).

**Suite conformance audit** (`qa/<stack>/skills/standards-audit` — **`dotnet` only so far**; java/typescript per `CONFORMANCE-AUDIT-PLAN.md`)
- `standards-audit` — the whole-suite, read-only, re-runnable audit of a **test suite** against this domain's own conventions: 14 lettered sections A–N (suite lane · naming/structure/comments · independence · waits · page objects · locator hygiene · test data · API layering · assertions · external verification · config/secrets · reporting & flake · CI wiring · coverage shape), saved to `docs/audits/<NNN>-qa-<stack>-conformance-r<N>.md` with `file:line` evidence, per-section rollups, defect families, and a leverage-ordered priority table. Loads the shared `ep-standards-audit-engine` engine (modes, evidence rules, severity, report templates) and supplies the rule set. **THE FENCE: it audits test code only** — the application under test belongs to `be-*`/`fe-*` and their audits, and a defect the suite exposes is a bug report, not a conformance finding. Rolls the per-family `*-test-author/reviewer` + `bdd-reviewer` checklists up to suite scale; read-only, so the `qa-*-<stack>` agents apply every fix. Entry points: `/qa-dotnet-audit`, or the single-skill trigger in `qa-api-dotnet` / `qa-ui-dotnet`

New-project setup = copy `qa/<stack>/` + `qa/manual/` + `qa/reporting/` + `qa/cicd/` + `qa/_shared/`.

Writes no code — java · dotnet · typescript

The upstream half of the backend domain: it turns a business case, a requirements set, or a loose direction into an ordered task list an agent can execute — and it **writes plans, never code** (its write reach is `docs/plans/<NNN>-<initiative>/**` plus its orientation cache; `Bash` is read-only). Two properties earn the invocation: the **approval gate is real** (Step 1 presents the blueprint, asks its open questions with 2–4 concrete options each, and *blocks* — nothing in Step 2+ is written on an unapproved architecture), and **every task names its executor** by exact catalog agent name + the skills it loads, which is what makes the pack runnable inline, by a `be-*` agent, or by Mission Control.

**Eight steps:** 0 Discover & orient (cache → stack/DB version detection → inventory existing plan artifacts + code → **classify the entry mode**) → 1 Blueprint *(blocking gate — now also covering actors, primary tasks and the app-shell proposal)* → 2 Data model → **3 Experience plan** (skipped, stated, when nothing is user-facing) → 4 API surface → 5 Integrations → 6 Delivery plan → **7 Explain** (a `-explained.md` companion per artifact) → 8 Self-review (area coverage · endpoint↔model consistency · screen↔endpoint consistency · journey coverage · **every cited agent/skill name resolves** · dependency sanity · placeholder scan · question closure · **companion fidelity**).

**Four entry points**, mapped onto the library's standard two modes: **NEW** (greenfield, nothing exists) · **DETAIL** (a high-level plan exists — human-written, or `ep-brainstorming`'s spec, or a prior `blueprint.md` — so Step 1 validates and normalizes instead of authoring) · **RESUME** *(Mode A)* — a detail pack **and** partial implementation exist, so the run opens with the **reconcile procedure**: every task verdicted `Done`/`Partial`/`Not started`/`Diverged`/`Blocked` with `file:line` evidence read **that session**, because *the plan is a lead, not evidence*; a `Diverged` task always escalates to the human rather than being silently rewritten to match the code · **EXTEND** *(Mode B)* — a new functional area appended with the next free IDs, never renumbering. The common real case (a high-level plan *plus* half-built code) resolves to **DETAIL grounded in the code**.

**The 6 planning skills** (`backend/_shared/<skill>/`, one artifact each — plus the shared `plain-language-companion` in Step 7, all landing in `docs/plans/<NNN>-<initiative>/` under the *target* project):
- `solution-blueprint` → `blueprint.md` — functional-area decomposition · architecture style with the *earned-complexity* table (modular monolith is the default proposal) · **the key flows and decision tables** (process flowcharts with named actors and *every* exit labeled including the failure exit; decision tables with a **declared DMN hit policy** plus completeness/overlap checks — an invented precedence rule is a business decision made silently, so an undecided policy is a `[TBD]` and an open question; depth delegated to `ba-process-flow-diagram` / `ba-decision-table`, now bundled) · tech stack with every row marked `detected`/`stated`/`proposed` · external systems at architecture altitude · **the routing map** (area/concern → exact library agent + skills, with the full agent catalog inlined so names are picked, not invented) · non-functional targets (the tenancy model is load-bearing) · risks · assumptions · open questions → **the gate**
- `data-model-plan` → `data-model.md` — conventions fixed **first** (UUIDv7 ids, money as minor units, UTC, soft-delete off by default, tenancy, concurrency, enums, naming — the project's existing convention always wins) · entity catalog · per-table column/key/index specs where **every index names the query it serves** and every FK states its delete behavior · ER + state diagrams · seed data · migration sequence mapped to delivery tasks (expand-contract for changes to a live schema)
- `experience-plan` → `experience-plan.md` — **the user's side of the system, planned before the API** (discipline: `design/ux-patterns`, loaded as the one design-layer exception to the planner's fence): actors & primary tasks (verb + object + outcome, frequency, stakes — every blueprint capability becomes a task) · app shell decided once with its rejected alternative + the nav map (depth budget: primary tasks one click from the shell, nothing at depth three) · journeys per primary task (screens → actions → endpoints, **steps counted against a target**, failure exit named) · a screen catalog `S1…Sn` (route, page type, surface, primary action, regions each with four states, data needed in the user's nouns — the line the API step turns into response fields and computed aggregates) · the **screen ↔ endpoint matrix** the API step fills (every user-facing endpoint on a screen, every data need resolved — two Step-8 coverage lines) · cross-cutting decisions (density, accelerators, notification surface, first run) and the **responsiveness budget** every frontend task inherits as acceptance criteria. The `fe-*` agent takes §2–§4 as its Step-1 IA decision (validates, never redesigns).
- `api-surface-plan` → `api-surface.md` — API-wide contract · the three-level **service → resource → endpoint** table (state transitions modelled as `POST /res/{id}/action`, never `PATCH {status}`; the Auth column is `qa-security`'s BOLA map) · per-endpoint typed request/response field tables (the Swagger equivalent) · shared schemas · `references/validation-catalog.md` — the standard set defined **once** and referenced per endpoint as **"standard set, plus —"**: RFC 9457 ProblemDetails envelope · request-shape 400/415/413 · field validation · the uniform **401** set (expiry the only permitted distinction) · **403** incl. BOLA/BFLA · the **exists → visible → valid-state** id chain with the 404-vs-403 disclosure decision · 409/412/428 conflict & concurrency · 429 · 5xx · the pagination contract. It is deliberately shaped as a ready-made negative-test matrix for `qa-api-<stack>`
- `integration-plan` → `integrations.md` — dependency register with a three-value **criticality** (critical/degraded/optional, each a design commitment) · per-dependency auth, config **key names and secret locations but never values**, environments, limits, timeout/retry/circuit-breaker, inbound-webhook rules (raw-body signature check, replay window, event-id idempotency), PII crossing the boundary, local-dev/test strategy · category rules (email/SMS, payments, IdP, storage, brokers, search, partner APIs) · the consolidated secrets checklist · the **failure matrix** (slow / down / returns garbage) · and the rule that every **blocking unknown** exists in three places at once — register row, open question, **and a prerequisite task**
- `delivery-plan` → `delivery-plan.md` + `HANDOFF.md` — tasks derived **mechanically** from the pack (never brainstormed) · **one flat, ordered task list** — the unit of work is a **task** (`T1…Tn`), never a slice, never a phase, and there is no grouping layer above it: ordering safety is position + explicit `Depends on` edges, since with no barrier an unwritten edge does not exist · **every task states one `Deliverable`** — the observable thing that exists when it is done, written as a result rather than an activity, and it is what `Done` means · **two sequencing shapes**, the choice stated in the artifact: **feature-complete** — the default for user-facing work, where the foundations built first are only those the *first* capability needs and each capability's tasks then run back to back, the **last one delivering something a person can actually exercise end to end** (its deliverable is the behavioural sentence, over the whole Step-1 capability set — schema · rules · endpoints · validation · authorization · wiring · unit tests · reachability — with any deferred foundation named rather than implied) — and **platform-first**, the layered shape (prerequisites → foundations → schema → cross-cutting → one task per resource → integrations → hardening) for service/platform initiatives with no user journey at stake · **tasks sized by coherence, not volume** (no file/criterion cap — one task, one deliverable; split only where it stops being one thing, and every piece must still build and be independently verifiable; a large task's acceptance criteria *are* its step breakdown) · **streams**: named lanes that keep their identity down the whole plan, each defended as *internally sequential* in one concrete sentence, with any two tasks sharing a file forced into one lane or joined by a dependency edge, and a run-wide unique `order` fixing the sequence · per-task deliverable + agent + skills + stream + order + files + dependsOn + checkable acceptance criteria citing the pack by section · the 6-value status vocabulary where `Done` requires `file:line` evidence · the reconcile procedure · **the plan is the progress record**: once implementation starts the executing agent maintains status + evidence (§2), ticks criteria in place (§3), appends to the **execution log** (§6, append-only — never edited, never deleted) and records **decisions & deviations** (§7, the thing most valuable and most often lost), all inside `delivery-plan.md`, because it is the document that outlives the session · `references/handoff-template.md` — **`HANDOFF.md` answers one question only: what to pick up next** (the next task per unblocked lane and where inside it to start, blockers with owners, stamped working-tree state, resume instructions), rewritten wholly every session and holding no history of its own · plus a **"For Mission Control"** ingestion block

**The Mission Control contract:** `delivery-plan.md` is written in exactly the vocabulary MC's planner consumes — run-level `streams[]` (`id · name · description`), per-task `id · streamId · order · title · deliverable · intent · acceptanceCriteria[] · agent · skills[] · files[] · dependsOn[]`, and `openQuestions[]` with 2–4 options each and one recommended — so the pack pastes in and maps ~1:1. **There is no phase level and no `parallelSafe` flag** (removed 2026-08-20 with the flat-task-list rewrite — a breaking change on the MC side): concurrency is `streams[]` + `dependsOn[]`, and ordering is `order`. Streams are therefore mandatory, not an optimization — a pack without them gives MC nothing to derive lanes from and runs one lane wide. Stream data is judged all-or-nothing: every task carries `streamId` + `order`, or none does, and a task in an undeclared stream costs the plan every lane it authored. An invented agent or skill name is the single most damaging defect in the pack, because MC binds on that string; Step 6 checks it explicitly.

**Fences.** vs `ep-brainstorming` + `ep-writing-plans` — those are the generic stack-agnostic chain; `be-planner` is the backend specialization producing a multi-artifact pack with API/DB/integration depth, and its Step-1 gate satisfies `ep-brainstorming`'s HARD-GATE under that skill's own step-by-step-agent scope clause. vs `data-architect` — the planner produces the **logical** model and migration ordering; engine selection, DDL, index strategy, RLS, and partitioning route to `data-architect`. vs `requirements-author`/`business-analyst` — **upstream**; the planner consumes their artifacts (`docs/business-model/`, epics, stories) and routes back to them rather than inventing requirements. vs `code-auditor` — when a RESUME reconcile finds systemic drift rather than a handful of divergences, that is an audit, not a reconcile. vs `devops-engineer` — the planner lists config keys and where secrets belong; it never provisions them.

**The reverse lane — `be-documenter`** (`backend/_shared/agents/be-documenter.md`, command `/be-documenter`, bundled into the three `be-*` plugins **and** `business-analysis`). `be-planner` run backwards: given a backend nobody wrote requirements for, it recovers the requirements the code *implies* — what the system does, for whom, under what rules, and what happens when things go wrong — written so a product manager or support lead can read it. Output goes **into the project's BA knowledge base** (`docs/business-model/`) under `ba-project-memory`'s contract, not into a parallel doc tree.

**The three-tier evidence rule is the whole agent.** Reverse documentation fails in exactly one way — stating business intent the code cannot support, in a document that then gets treated as authoritative — so every statement is tiered using the KB's existing confidence grammar: **`#observed`** (what the code does, with a `file:line` read *this session*) · **`#inferred`** (what it is probably for) · **`#confirmed`** (a human said so). **It writes `#observed` and `#inferred` only and never emits `#confirmed`** — promotion is a human act — and **every `#inferred` intent is simultaneously a row in the open-questions list**, which for a business reader is often the run's most valuable output. It never overwrites a `#confirmed` entry: a human's confirmation outranks a trace, so a contradiction is escalated, never resolved.

**Six steps:** 0 Orient (cache → stack detection → **read the existing KB** → declare mode FULL / AREA / REFRESH) → 1 Survey *(blocking gate — the human confirms the area split, since area names derived from code are the most likely thing to be wrong and every artifact is filed under them)* → 2 Trace → 3 Model → 4 Write (one simple document per area) → 5 Consolidate → 6 Self-review (coverage · evidence spot-check · tiering · **worked-example arithmetic recomputed** · language · KB contract · reachability · contradictions).

**The 3 skills** (`backend/_shared/`): `codebase-survey` — inventories **every** way the system can be made to act (HTTP entry points, scheduled jobs, queue/event consumers, domain modules, persistence, external clients, auth surfaces, feature flags, admin paths — background work and consumers are where undocumented rules concentrate, since no UI exposes them), groups them into functional areas **by business capability, never by technical layer** (`Ordering` is an area; `Controllers` is not), and produces a **coverage ledger** where every surface is assigned or explicitly parked, plus a reading plan ordering identity/actors first · `feature-trace` — walks each entry point through the 10-stop path (entry → authorization → validation → preconditions → orchestration → **domain rules** → persistence → external calls → events → failure paths) into six inventories (capabilities · business rules · validations & gates · entity states incl. **refused** transitions · decision points · integrations with their failure behavior), every item `file:line`-evidenced, with `references/trace-recipes.md` cataloguing where rules hide (guard clauses, DB constraints, scheduled jobs, event handlers, config/flags, constants/seed data, tests-as-intent) plus the **silent-rule catalogue** (rounding, timezone boundaries, defaults, ordering/tie-breaks, retry/idempotency, soft-delete visibility, tenancy scope) and per-stack search patterns · `business-documentation` — **one simple document per area in a fixed shape** (overview with its one governing *Important:* line · scope & boundaries · setup parameters with layered precedence and validations · how it works as **one flow per trigger**: numbered steps, plain-text formulas with `Where:` and rounding/conventions stated, the result for the user · **a full worked example with real numbers, arithmetic recomputed** · who can do what · open questions · a closing **evidence table** that is the only home of `file:line`, tier tags and code nouns — optional sections dropped, never padded), plus `system-overview.md` with the end-to-end flows that cross areas, the glossary's **code-name → business-name mapping** (drift is a finding, never a silent merge), and a mandatory **provenance stamp** so generated content is distinguishable from hand-authored at a glance.

**Loaded, not owned:** `ba-project-memory` (mandatory every run — it owns the KB layout, IDs, grammar, and read-first/update-after contract) plus `ba-process-flow-diagram` / `ba-entity-state-grid` / `ba-decision-table`, which produce the `FLOW-`/`ENT-`/`DEC-` artifacts in Step 3; the documenter supplies evidence and links them by ID rather than re-authoring or duplicating them. All four are now bundled into the `be-*` plugins.

**The language discipline** is what separates documentation the business uses from documentation it politely ignores: narrative sections carry **no class names, table names, HTTP status codes, exception types, or framework nouns** — "you can only cancel an order that has not yet shipped", never "`CancelOrderHandler` throws when `status == Shipped`". The technical anchor lives in the closing evidence table, where an engineer can verify it.

**Fences.** vs **`ep-feature-audit` / `code-auditor`** — the nearest neighbour and the one users will conflate: *same tracing technique, opposite question and audience*. The audit asks "what is wrong with this" and writes findings for engineers into `docs/audits/`; the documenter asks "what does this do and for whom" and writes documentation for the business into `docs/business-model/`. A feature-audit report is a first-class **input** to a trace, and the documentation is what a later spec-vs-code audit verifies **against**; defects found while tracing are reported, never written up as intended behavior. vs **`business-analyst`** — it *owns* the KB and all cross-feature conflict reasoning; the documenter **populates** the KB from code and hands off, never resolving a conflict or inventing precedence. vs **`requirements-author`** — that authors intent for work to be done; this recovers intent from work already done. vs **`be-planner`** — the forward direction, and the natural next step: a documented legacy system is exactly what an EXTEND run needs to respect. **Read-only on code** — write reach is `docs/business-model/**` plus its orientation cache, `Bash` is inspection only, and unreachable code is reported as unreachable rather than documented as a capability.

**The planner's closing lane — `be-shared-plain-language-companion`** (`backend/_shared/plain-language-companion/`), which `be-planner` loads as the last step before self-review. The planning pack is written to be *precise* — typed endpoint contracts, agent-bound tasks — and that precision is exactly what makes it unreadable to the person who owns the business it describes. So each plan artifact gets a companion beside it under one convention: **the source's own filename plus `-explained`** (`blueprint.md` → `blueprint-explained.md`, and likewise for `data-model` / `experience-plan` / `api-surface` / `integrations` / `delivery-plan`; `HANDOFF.md` and `references/` get none). **Two disciplines carry it.** *Derived, never independent* — the companion contains no rule, threshold, entity, endpoint, task or decision the source lacks; if writing it makes you want to state something new, that is a gap in the **source**, fixed there. Every companion opens with a mandatory header declaring precedence (*if the two disagree, the source is right and this file is out of date*), the source's pinned commit + date, and the line that the examples are made up. *Examples are the payload* — the rule is the source's, the walk-through is the companion's, and every **number used as a rule is quoted exactly** while only the incidental (names, dates, order numbers) is invented, with one running cast per document. Companions are **regenerated wholesale, never patched** — an orphan is deleted, a stale one is banner-marked. Each artifact's companion answers exactly one question and drops the machinery (`delivery-plan-explained.md` keeps every deadline, threshold and blocker, and loses task ids, file lists and agent names). One companion moves earlier by design: where the human approving `be-planner`'s Step-1 gate is non-technical, `blueprint-explained.md` is written alongside `blueprint.md` and presented with it — an approval given on a document the approver could not read is not an approval. **The documentation lane gets no companion:** `be-documenter` and `be-feature-documenter` documents are written in the plain, example-first shape to begin with, so a companion would be a second copy.

**The feature-scale sibling — `be-feature-documenter`** (`backend/_shared/agents/be-feature-documenter.md`, command `/be-feature-documenter`, bundled wherever `be-documenter` ships: the three `be-*` plugins + `business-analysis`). `be-documenter` at feature altitude: given a **described feature** ("the refund flow", "password reset") rather than a whole system, it locates the implementation, runs the same `be-shared-feature-trace` engine over just those entry points, and writes **one standalone document** to `docs/features/<NNN>-<slug>.md` in the **same simple shape as an area document** (overview · scope · setup parameters · how it works as triggers → numbered steps → plain-text formulas → the result for the user · **a full worked example with real numbers** · who can do what · open questions & findings · a closing evidence table): the body in business language a non-technical reader follows top to bottom, every claim `file:line`-anchored and tiered `#observed`/`#inferred` in the table, never `#confirmed`. What it deliberately drops from the full lane: no `codebase-survey` (the description is the scope — its Step-1 gate is **proportional**: an unambiguous match states the scope table and proceeds, ambiguity blocks), no KB writes (`docs/business-model/` is read-only context whose `#confirmed` entries outrank the trace — contradictions escalate), no `ba-*` modelling artifacts (a heavily branching flow gets a Mermaid diagram embedded directly in the one document), and optional sections that don't apply are dropped with the search that proved it recorded as an evidence-table row, so absence still reads as verified. Read-only on code (write reach `docs/features/**` + its orientation cache). **Fences:** whole system or KB integration → `be-documenter` (AREA mode); "find the defects" → `code-auditor`/`ep-feature-audit` (same trace, opposite question — its Findings section is that audit's starting point); the document is a ready-made test basis for `qa-test-case-designer` and an existing-behavior input for a `be-planner` EXTEND run.

**Two `ba-project-memory` changes came with the reverse lane:** the KB layout gained `areas/<area>.md` (`AREA-nnn`) and `system-overview.md`, both owned by `be-shared-business-documentation` — plus the **provenance rule** and an explicit reconciliation of the "do not backfill speculatively" rule — evidence-based bulk backfill from code is the stated exception, because the rule forbids *speculation*, not *volume*.

**Stacks** (`backend/<stack>/skills/`, prefix `be-<stack>-*`; agent `backend/<stack>/agents/be-<stack>.md`):
- **`dotnet`** (.NET 10 primary / 8-9 supported) — `pattern-guide` / `pattern-writer` (Strategy, Decorator, Repository, CQRS/MediatR, Factory, Options, Pipeline) / `code-review` (DI/async/layering violations) / `database-code` (EF Core: `DbContext` design, configurations, migrations, query patterns, optimistic concurrency, bulk operations) / **`unit-testing`** (the dev-side in-process test lane for the logic this stack generates: NUnit 4 + NSubstitute + `FakeTimeProvider`, a selection matrix for what deserves a test, the five untestable seams (time · identity · randomness · config · outbound I/O — the constructive half of conformance check M2), fakes-over-mocks, parameterized cases, async assertions. **Fenced hard at the process boundary:** no HTTP, no container, no real DB, and never a stand-in for a real-DB integration test — that stays the `qa-api-dotnet` peer's) / `auth0` + `cognito` (service-side auth: JWT bearer validation via `AddJwtBearer`, RBAC via authorization policies, Client Credentials M2M — the ASP.NET Core sibling of `auth/auth0-blazor` / `auth/cognito-blazor`) / **`standards-audit`** (the whole-service, read-only, re-runnable self-audit — **dotnet only so far**, java/node per `CONFORMANCE-AUDIT-PLAN.md`: 14 sections A–N covering build/TFM lane · pattern application · DI lifetimes · async · state/immutability · layering · EF Core mechanics · API contract · service-side auth · resilience · config/secrets · **the bundled observability invariants** (bounded metric cardinality, Collector-as-the-seam, message-template logging) · testability · structure & comments, saved to `docs/audits/<NNN>-be-dotnet-conformance-r<N>.md`; loads the shared `ep-standards-audit-engine` engine, fences against `code-review` (one diff) and `code-auditor` (vs a spec) and the peer `qa-dotnet-standards-audit` (the test suite), and fixes nothing — the `be-dotnet` agent does, via `/be-dotnet-audit`'s priority table)
- **`java`** (Java 21 + Spring Boot 3.x) — same six skills, Spring-idiomatic (incl. **`unit-testing`** — JUnit 5 + Mockito + AssertJ with **no Spring context**: a `@SpringBootTest`/`@DataJpaTest`/`@WebMvcTest` slice test is fast but not isolated, so it is the `qa-api-java` peer's; the `Clock` seam is JDK-native. **Stated house deviation:** `CLAUDE.md`'s TestNG default is the *QA suite's* runner — dev-side unit tests use JUnit 5, because `spring-boot-starter-test` ships it) (constructor injection, `@ConfigurationProperties` Options, JPA/Hibernate + Spring Data + Flyway persistence, `@Transactional` boundaries, `@Version` optimistic locking, N+1 prevention; `auth0`/`cognito` via the Spring Security OAuth2 Resource Server + method-level `@PreAuthorize`)
- **`node`** (Node 24 active LTS primary / 22 maintenance supported; TypeScript strict) — the five pattern/persistence/test skills, TS-idiomatic (incl. **`unit-testing`** — Vitest, DI over `vi.mock`, **both branches of every `Result<T,E>`**, Zod `issues[].path`/`code` assertions, integer minor units for money; `mockDeep<PrismaClient>()` is called out as the trap it is — a query is only proven against a real engine) (discriminated unions + `Result<T,E>` over class hierarchies, branded ids, higher-order-function decorators, Zod at every boundary; Prisma default / Drizzle / TypeORM persistence); no `auth0`/`cognito` skill yet (gap — the Node backend currently has no service-side auth skill; `qa-test-login-tokens-typescript` exists but there's nothing for it to complement)

`dotnet`/`java`'s `auth0`/`cognito` skills load the cross-cutting `auth/_shared/{auth0-concepts,oidc-concepts}` for the provider-agnostic concept model, and hand off to `auth/auth0-{blazor,react}` / `auth/cognito-{blazor,react}` for the SPA/Blazor side of the same login flow — the frontend and backend halves of one integration, split by where the code runs.

Each stack agent runs the same pipeline — **pattern decision** (confirm the pattern is earned, not premature/stacked; detect the stack version) → **generate** (scaffold the pattern, persistence layer, and/or service-side auth wiring) → **unit test** (cover the logic just generated via the stack's `unit-testing` skill, in-process with no HTTP/container/real DB — **NUnit 4 + NSubstitute** · **JUnit 5 + Mockito + AssertJ, no Spring context** · **Vitest, DI over `vi.mock`**) → **review** (hostile senior review: pattern misuse, DI/async/type-safety violations, layering) — and is **brownfield-capable**: it orients on an existing codebase first (build/lint clean, seams to reuse), then only **fixes** a defect or **extends** existing work, re-entering just the touched step(s), per `.skill-template/agent.md`. All three carry the same **plan-execution lane**: when the work comes from a `be-planner` `delivery-plan.md`, the agent delivers the whole task *including what makes the capability reachable*, then writes progress back into the plan itself — §3 status + evidence, §4 criteria ticked in place, the append-only §7 execution log, §8 for anything diverged (escalated, never absorbed) — and rewrites `HANDOFF.md` down to what to pick up next. Re-sequencing stays `be-planner`'s.

**Peer handshakes** (named, not loaded): `qa-api-{java,dotnet,typescript}` write the contract/integration tests against the API a `be-*` agent implements (`qa-*-{java,dotnet}`'s `test-login-tokens` skill mints test tokens against the login flow a `be-*` auth skill validates); `qa-security` owns the DAST/SAST/SCA/access-control gates; `qa-cicd-{java,dotnet,typescript}` wires build+test into CI; `data-architect` owns schema/DDL/index design and cross-engine migration strategy whenever the persistence need goes beyond ORM mechanics — the backend `database-code` skill stays in its lane (EF Core / JPA / Prisma mechanics only).

New-project setup = copy `backend/_shared/` + the `backend/<stack>/` you need.

## Observability catalog

The `observability/` folder is the **telemetry** domain — the Grafana-stack sibling of `backend/`, distinct from `qa/` (which tests the service this instruments) and `data/` (which owns the schema). It is **not a standalone plugin**: its skills and agents are **bundled into the three `be-*` plugins** so a backend install carries observability with it. The design standardizes on the library's Observability default (root Stack defaults): **OpenTelemetry → Grafana stack** — Loki (logs), Prometheus/Mimir (metrics), Tempo (traces), all fed through a single **OTel Collector** as the seam, with cross-store navigation (exemplars metrics→traces, Loki derived fields logs→traces) as the payoff.

**Skill shapes.** Two, like the rest of the library:
- **Per-stack** (`opentelemetry-{dotnet,java,node}`, `structured-logging-{dotnet,java,node}`) — the instrumentation + logging skills, one implementation per stack (OTel .NET SDK + Serilog · OTel Java agent + SLF4J/Logback · `@opentelemetry/sdk-node` + pino). Version-aware to the stack's version policy.
- **Stack-agnostic** (`logs-traces-setup`, `metrics-setup`, `queries`, `dashboards`) — the backend + query + dashboard skills shared by all three stacks. `logs-traces-setup` stands up the Collector hub + logs/traces backend and log forwarding (**Grafana Alloy** default; Promtail is deprecated/EOL 2026); `metrics-setup` owns the metrics backend (Prometheus single-cluster vs Mimir multi-cluster/long-retention), exemplar storage, and rule *deployment*; `queries` owns query + recording/alert-rule *syntax*; `dashboards` owns panel layout + cross-store nav wiring.

**Agents** — one step-by-step **`observability-engineer-{dotnet,java,node}`** per stack, bundled into the matching `be-*` plugin as a sibling of the `be-<stack>` agent. Six steps: Discover (detect stack version + existing telemetry) → Backend setup (`logs-traces-setup` + `metrics-setup`) → Instrument (the stack's `opentelemetry-*` + `structured-logging-*`) → Query & dashboards (`queries` + `dashboards`) → Hostile review (cardinality audit, cross-store nav wired, no direct-to-backend exporters). Loads **only** `observability/*` skills (+ the bundled `ep-*` for brownfield); brownfield-capable (orient → FIX/EXTEND, re-entering only the touched steps) per `.skill-template/agent.md`.

**Peer handshakes** (named, not loaded): `be-{stack}` (the service being instrumented — sibling in the same plugin), `qa-cicd-{stack}` (CI wiring for the telemetry-emitting build), `qa/manual/quality-metrics` (the SLO/KPI math the recording rules encode), `devops/kubernetes` + `devops/infrastructure-as-code` (cluster manifests + object-storage buckets/IAM for the backends).

The two invariants every design holds: **bounded metric cardinality** (per-record ids — `order.id`, `user.id`, `trace_id` — are span attributes, never metric labels) and **the Collector as the seam** (apps export OTLP to the Collector, never straight to Tempo/Prometheus, so sampling/routing changes without an app redeploy).

## Data catalog

The `data/` folder is the **database-engineering** stack (distinct from `qa/`, which tests the data this designs, and from the backends that consume it). It is organized like the QA and Frontend domains — **engine-first, domain-encapsulated, one step-by-step orchestrator agent, one marketplace plugin** — and shipped as the self-contained `data` plugin. The **`data-architect`** agent (`data/agents/data-architect.md`) owns a data design end-to-end across six steps: discover (engine + version detection, workload shape) → model → secure → implement (DDL + migration) → tune (indexing/query) → hostile review. It loads **only** `data/*` skills; QA (`qa-api-{stack}` db-testing, `qa-security` for the cross-tenant leak test, `qa-performance-{stack}`) and `auth/*` (tenant claims → session context) are **peers** it names, not loads.

**Skill shapes.** Two, like the rest of the library:
- **Router + topic references** (`postgresql`, `sqlserver`, `mysql`, `mongodb`, `redis`) — the `SKILL.md` routes and holds the shared rules (version policy, connections/pooling, hard rules); depth lives in `references/<topic>.md` split by **topic** (`data-modeling` · `security` · `indexing` · `performance` · `caching`; Redis: `data-structures` · `patterns` · `security` · `operations`). Unlike qa's one-of-N families, a task may need **two** references at once (a new multi-tenant schema = `data-modeling.md` + `security.md`). **Read the router first, then the matching reference end-to-end before writing code.**
- **Single-file** (`dynamodb`, `cosmosdb`, `elasticsearch`) — their models don't decompose the same way, so each is one file with topic sections.

**Engines** (`data/<engine>/`, skill name `data-<engine>`): `postgresql` · `sqlserver` (Azure SQL) · `mysql` (MariaDB / Aurora) · `mongodb` · `redis` (Valkey) · `dynamodb` · `cosmosdb` · `elasticsearch` (OpenSearch). Fork-divergence is called out where it matters — MariaDB↔MySQL · Valkey↔Redis · OpenSearch↔Elasticsearch.

**Cross-engine `_shared/`** (`data/_shared/<skill>/`): `schema-design` (id strategy / money / soft-delete / multi-tenant pattern choice / embed-vs-reference) · `migrations` (expand-contract universal pattern + tool-selection table) · `caching-patterns` (cache-aside / stampede / TTL & key policy) · `slow-query-fixes` (universal triage / ESR / keyset / N+1).

**The scope-fence contract** (checked every design): `_shared` owns the cross-engine **decision/pattern**, the engine skill owns the **mechanics**. Modeling — `_shared/schema-design` decides id strategy (UUIDv7 default), tenancy pattern, embed-vs-reference; the engine `data-modeling` executes the DDL / native generator / modeling mechanics. Migrations — `_shared/migrations` owns expand-contract + the tool table; the engine owns online-safe DDL (`CONCURRENTLY`, `NOT VALID`, pt-osc/gh-ost). Caching — `_shared/caching-patterns` owns the strategy; the engine `caching` (and Redis command mechanics) own the invalidation/change-channel seam. Query tuning — `_shared/slow-query-fixes` owns universal triage; the engine `performance`/`indexing` own plan-reading and index types.

**Peer handshakes** (named, not loaded): `qa-api-{java,dotnet,typescript}` `db-testing/{client,testcontainers,verification-queries}` seed/assert/clean against the schema; **`qa-security` owns the cross-tenant leak test** (BOLA/IDOR/BFLA) that proves Step-3 isolation holds — MySQL/Mongo app-enforced tenancy makes this leak test *mandatory*, since there is no RLS to fall back on; `qa-performance-{stack}` validates Step-5 tuning under load; `auth/auth0-{stack}` + `auth/_shared/auth0-concepts` supply the tenant/user claims feeding the RLS / app-enforced session context.

## DevOps catalog

The `devops/` folder is the **platform / delivery** domain — the path from a built service to a running one. It sits beside `backend/` (which writes the service) and `observability/` (which instruments it), and is shipped as the self-contained **`devops`** plugin. Unlike the stack-first domains, devops is **cloud-keyed, not stack-triplicated**: the skills wrap Dockerfiles, IaC, cloud primitives, and pipeline YAML, none of which split usefully three ways, so there is **one skill per tool/cloud** and **two stack-agnostic agents** — one that builds, one that audits. Skill names carry the `devops-*` prefix.

**The gate both agents share — confirm the tool stack before loading any skill.** Because devops skills are *keyed to tools rather than stacks*, picking which to load **is** the design decision, and an infrastructure guess is expensive to unwind. So both agents run the same mandatory two-step opener: **Step 0 Discover** (read-only repo inspection — existing image/IaC/manifests/pipeline/config, stack version lane, cloud, CI host — plus deriving what the workload actually requires, or which audit sections apply) → **Step 1 Confirm** (present a proposal table with every row marked `detected` / `stated` / `proposed`, and **block on the human's answer**) → only then load the skills the confirmed answer selects, and nothing else. No `SKILL.md` is read and no file is written before Step 1 has an answer; the gate is proportional (a fully-`detected` single-service repo gets a one-word confirmation), runs once (no mid-run re-litigation), and honours a confirmed choice you disagree with after stating the concern once.

**Skills** (`devops/<skill>/`, name `devops-<skill>`):
- **Image** — `docker` (multi-stage builds, base-image choice per detected version, layer optimization, non-root + healthcheck, image scanning)
- **Infrastructure** — `infrastructure-as-code` (Bicep for Azure-only stacks, Terraform for AWS/multi-cloud; module structure, remote+locked state, `prevent_destroy`) · `kubernetes` (manifests, Helm, Kustomize overlays, Deployment/Service/Ingress/HPA/PDB, IRSA / Workload Identity, for AKS/EKS/GKE)
- **Deploy** — `aws-deployment` (ECS Fargate default, Lambda, App Runner, S3+CloudFront with OAC, EKS) · `azure-deployment` (Container Apps default, Functions, App Service, Static Web Apps, AKS). Each opens with a primitive-decision matrix keyed to workload shape
- **Pipeline** — `github-actions` · `gitlab-ci` · `azure-pipelines` (kept as three full authoring surfaces rather than a one-of-N router: each is a 300+ line surface, the host is repo-determined so no decision matrix is needed, and ~10 inbound references already point at the three paths)
- **Config** — `environment-config` (typed config classes, secret stores — Key Vault / Secrets Manager / Parameter Store / Vault, layering defaults → per-env → secrets, startup schema validation, hot-reload)

**Agents** — three stack-agnostic peers. **The build agent produces; the audit agent finds and never fixes; the infra-security tester benchmarks and probes and never fixes.**

- **`devops-engineer`** (`devops/agents/devops-engineer.md`) — seven steps: **0 Discover** (read-only inventory + workload shape) → **1 Confirm** (the gate: container · orchestrator · cloud · deploy primitive · IaC tool · CI host · config & secrets store · environments, signed off by the human) → **2 Containerize** (`docker`) → **3 Provision** (`infrastructure-as-code`, + `kubernetes` for k8s targets) → **4 Deploy** (`{aws,azure}-deployment`) → **5 Pipeline & config** (the confirmed CI host + `environment-config`) → **6 Hostile review** (OIDC-only audit, pinned tags/digests/actions, non-root + probes + resource requests, min-replicas, tags on every resource, remote+locked state, no plaintext secrets). Loads **only** the `devops/*` skills the confirmed stack selects (+ the bundled `ep-*` for brownfield); brownfield-capable (orient → FIX/EXTEND, re-entering only the touched steps) per `.skill-template/agent.md`. Command: **`/devops-engineer`**.
- **`devops-auditor`** (`devops/agents/devops-auditor.md`) — the **read-only CONVENTION-lane sweep** of existing delivery infrastructure against these same nine skills' rules, five steps: **0 Discover** (which surfaces exist, which version lane, Mode A or B) → **1 Confirm** (the gate, here settling three things: **section scope** · **repo scope** in a monorepo · **evidence mode**, which is static by default — `terraform plan` / `docker build` / `kubectl` / live-cloud CLI reads are each a *named* opt-in) → **2 Sweep** → **3 Report** → **4 Hostile self-review**. **Twelve lettered sections A–L**, each naming the skill that owns its rules: version & runtime lane · container image · Kubernetes workloads · IaC · cloud deploy primitive · pipeline · **identity & credentials** · config & secrets · **pinning & reproducibility** · environments & promotion · resilience & operability · scope-fence handoffs. The two plugin invariants (G and I) are **blocker-class by default**. Saves `docs/audits/<NNN>-devops-conformance-r<N>.md`; **fixes nothing** — `devops-engineer` applies every finding, citing the IDs. Command: **`/devops-auditor`**.
- **`infra-security-tester`** (`devops/agents/infra-security-tester.md`) — the **offensive-leaning posture tester**, the cloud-native infra-security sibling of `devops-auditor`: where the auditor reads files for static conformance, this one runs **benchmarks and live probes** that prove isolation and controls actually hold. Seven steps: **0 Discover & threat-model** (surface map + run `threat-modeling` to scope the rest) → **1 Confirm scope & authorization** *(blocking gate — static posture runs freely; any **live cluster / cloud / runtime** probe needs a recorded, `#volatile`, owned-target authorization line with an expiry, `kube-hunter --active` and production each a separate louder sign-off)* → **2 IaC & image posture** → **3 K8s & runtime** → **4 Cloud posture & IAM** → **5 Controls validation & retest** → **6 Evidence-based findings + remediation handshake**. **Two spines, keyed to the surface:** CIS benchmarks + OWASP for misconfig; the MITRE ATT&CK **Containers** matrix for K8s/container findings and the **Cloud** matrix for cloud/IAM findings. **Read-heavy and retest-capable, never fixes** — `devops-engineer` applies remediation, then this agent re-runs the check (RETEST mode). Loads only the seven Stage-1 skills (below) + `image-infra-scan` for the Trivy CVE half + the bundled `ep-*`. Saves `docs/security/<NNN>-infra-security-r<N>.md`. Command: **`/infra-security-tester`**.
- **`security-test-planner`** (`security/agents/security-test-planner.md`, command **`/security-test-planner`**) — the **security counterpart to `be-planner`** and the **entry point to the whole security domain**: given a platform (a repo · a running system/URL · a cloud account/cluster · a loose description), it discovers the attack surface, **blocks for a scope + authorization sign-off**, then emits an **assessment plan whose tasks are independently executable** and each **bound to the exact lane agent that runs it** (`infra-security-tester` + its seven skills · `qa-security` + its scanners + Stage-2 `exploit-validation`/`vuln-reachability`/`client-side-security` · `penetration-tester` + its seven kill-chain skills · `purple-team-engineer` + its two purple-team skills · `security-architect` + its four governance skills — **all security lanes now built**; an unbuilt future executor is still named and marked, never invented). It lives in the `security/` domain and is **homed in the `penetration-testing` plugin** (relocated there from its interim `devops` home when the `security/` domain shipped at Stage 3, 2026-08-16). Fences: vs `be-planner` (plans *build* work bound to `be-*`; this plans *assessment* work bound to security lanes) · vs the lane agents (it routes and sequences; they scan/exploit/report) · vs `security-architect` (the planner runs *before* to sequence, the architect *after* to roll findings into a posture picture).

**The seven infra-security skills** (`devops/<skill>/`, name `devops-<skill>`, all language-agnostic — the tools are Docker/CLI binaries, so single skills routing to `references/<tool>.md`, never stack-triplicated): `threat-modeling` (STRIDE · DFDs · attack-trees → a threat register that routes each threat to the lane that tests it; run first, it scopes every downstream lane and closes the `qa-security` Step-1 forward-wire) · `iac-security` (Checkov · OPA/Conftest · tfsec/Terrascan/KICS — deep Terraform + **policy-as-code**, the org-rule layer beside Trivy's built-in `config` scan) · `k8s-security` (kube-bench CIS · Kubescape NSA/CISA-MITRE-CIS · Polaris · kube-score — benchmark scoring + RBAC/network-policy/pod-security **isolation validation**) · `container-runtime-security` (kube-hunter attack-surface probing incl. the loud `--active` mode · Falco runtime detection — the runtime, not static, surface) · `cloud-posture` (Prowler + ScoutSuite CSPM across **AWS → Azure → GCP**, one `references/<provider>.md` each; commercial Wiz/Prisma/Defender named as references) · `supply-chain-security` (cosign/sigstore keyless signing · SLSA provenance/attestation · dependency-confusion/typosquat — OWASP A08, the integrity half beside Trivy's SBOM generation) · `infra-controls-validation` (scripted **present-AND-effective** checks for secrets/encryption-in-transit/monitoring/pipeline-hardening — validates a control *works*, not just that it exists, and retests after a fix).

**The fence between them:** `devops-engineer` writes infrastructure and owns remediation; `devops-auditor` is read-only (`Write`/`Edit` reach the report and nothing else) and owns evidence. Against the neighbouring lanes — `code-auditor` owns code-vs-spec and spec-less feature traces; `qa-security` owns *proving* exploitability (the auditor only inventories whether the gates exist); `qa-cicd-{stack}` owns auditing the test-suite lane; the `be-*`/`fe-*` standards audits own application code.

**The two invariants every design holds:** **no static cloud credentials** (OIDC / Workload Identity Federation from the pipeline; Managed Identity / IRSA / task role at runtime — a long-lived key is a blocker finding) and **pin everything** (base images by tag, actions/tasks by major or SHA, language versions to what the project targets, the pnpm version sourced from `package.json` `packageManager` and never double-pinned in CI).

**The scope fence users trip on — deploy lane vs test lane.** `devops/{github-actions,gitlab-ci,azure-pipelines}` own the **build/deploy** pipeline; `qa/cicd/<stack>/skills/ci-pipelines` + `qa-cicd-{stack}` own the **test-suite** lane (shard matrix, Allure publishing, perf gate, flake quarantine). All three devops CI skills upload raw test results as artifacts and hand off — they never generate or publish an Allure report.

**Peer handshakes** (named, not loaded): `be-{dotnet,java,node}` (the service being shipped — build command + artifact path), `observability-engineer-{stack}` (devops provisions the buckets/IAM their backends need), `qa-cicd-{stack}` (the test lane in the same pipeline file), `qa-security` (`qa-security-image-infra-scan` owns the Trivy gate policy; devops wires the image build it scans), `data-architect` (devops provisions the server/network/identity; data-architect owns the schema), `fe-{blazor,react}` (static-hosting target + build output directory).

## Security catalog

The `security/` folder is the library's dedicated **security domain**, homed as **two plugins that are two lanes**: the **offensive** `penetration-testing` lane and the **defensive/governance** `security-governance` lane (the folder is the domain, the plugins are the packaging — exactly as `qa/` fans into three `qa-*` plugins). Everything here is language-agnostic (every tool is a Docker/CLI binary — single skills, never stack-triplicated).

**The offensive lane — `penetration-testing`** (born at Stage 3, 2026-08-16), the live, authorization-gated penetration-testing lane the defensive lanes hand off to. It is the offensive counterpart to `qa-security` (which detects, weights, and proves a *single* vuln) and `infra-security-tester` (which benchmarks and probes infra *posture*): where those stop at detection/proof/posture, it runs the **full kill chain** — recon → exploitation into a foothold → privilege escalation → lateral movement → post-exploitation capped at proof — to prove an attacker could actually chain the findings into impact. As of Stage 4 (applied 2026-08-20) the plugin also homes the **purple-team lane** (below) — three step-by-step agents (`penetration-tester` + `security-test-planner` + `purple-team-engineer`), one marketplace plugin.

**The load-bearing safety model — the whole design (`SECURITY-EXPANSION-PLAN.md` §5, owner-signed-off).** Offensive execution is trustworthy only while nine controls hold, enforced by both agents and every skill: (1) a **committed engagement scope file** `docs/security/engagement-<NNN>.md` (in-scope hosts/CIDRs/accounts · hard exclusions · allowed techniques · blast-radius cap · data-handling · window · named authorizer) the agent refuses to start without and re-reads before every step; (2) **`#volatile` authorization** — expires with the window, re-confirmed each run, never cached; (3) **destructive/irreversible acts opt-in per act** — no data destruction, **no DoS ever**, no persistence left behind, no C2 beyond the authorized env; (4) **cleanup verification** a required report section; (5) **owned/throwaway infra only**, restated per skill; (6) **production a separate, louder second sign-off** than lab (lab/throwaway is the default target); (7) **loot never lands in the repo** — report *that* a secret was recovered + its blast radius, never contents; (8) a **full action log** a required report section (what payload/command, against what, when); (9) a **defined mid-run abort** — a next act outside scope halts the run and reports, never silent scope-narrowing. Two spines: **MITRE ATT&CK Enterprise** (this is a host/app kill chain — not the Cloud/Containers matrices `infra-security-tester` uses) + **CVSS** — the deliberate, documented divergence from the library's blocker/major/minor/nit table (stated once in `pentest-reporting`, the way `be-java` documents its JUnit-vs-TestNG deviation). Dual-use skills (`credential-attacks`, `post-exploitation`) lead with the authorized-lab-only + defensive-intent framing; persistence is demonstrated then removed and logged; C2 stays in the authorized env.

**The 7 skills** (`security/<skill>/`, prefix `pentest-*`, each self-contained, each opening with the §5 authorization + scope-file gate): `recon-enumeration` (attack-surface — amass · subfinder · httpx · nmap · masscan · Shodan/Censys reads; passive-first, rate-bounded) · `initial-access` (exploitation into a foothold — Metasploit · sqlmap at foothold altitude; consumes a `qa-security` `exploit-validation` single-vuln proof as feedstock — the boundary is single-vuln-proof vs foothold-at-network-altitude) · `privilege-escalation` (linPEAS/winPEAS · GTFOBins/LOLBAS · kernel/sudo/SUID + Windows token/Potato chains) · `lateral-movement` (NetExec/nxc — the CrackMapExec successor · impacket · BloodHound CE + SharpHound/AzureHound · ligolo-ng/chisel/sshuttle/SSH pivots · compromised-pod → kube-API pivots) · `credential-attacks` (hashcat offline · hydra online · Responder LAN capture · LSASS/cloud/IMDS/AD harvesting — all loot-redacted) · `post-exploitation` (data-access proof · persistence demonstrated-then-removed · Sliver/Mythic C2 — capped at proof) · `pentest-reporting` (executive + technical, CVSS + ATT&CK, remediation, proof, action log, cleanup verification).

**The agent — `penetration-tester`** (`security/agents/penetration-tester.md`, command `/penetration-tester`): the red-team orchestrator, sequenced strictly — **0 Rules-of-engagement & scope file *(blocking gate)* → 1 Recon → 2 Exploitation → 3 Priv-esc → 4 Lateral movement → 5 Post-exploitation (capped at proof) → 6 Report + cleanup verification.** Each step re-reads the scope file and cannot act outside it. Loads only the Stage-3 skills + the always-on `ep-*`; **never fixes** (the `be-*`/`fe-*`/`devops-engineer` agents apply remediation; it retests). Saves `docs/security/<NNN>-pentest-r<N>.md`. **The planner — `security-test-planner`** (relocated here from its interim `devops` home) is the domain's entry point: it discovers a platform, blocks for scope + authorization, and emits an assessment plan binding each task to its exact lane agent (see its Backend/DevOps-catalog description).

**The purple-team lane — `purple-team-engineer`** (Stage 4, applied 2026-08-20): continuous **detection validation** — the standing proof that the guardrails actually fire. It is the **purple bridge** between the offensive kill chain and the defensive/governance lane: for each technique in a chosen ATT&CK set it **detonates it (red)** against an authorized lab/owned environment and then **immediately asserts the SIEM/guardrail/alert fired (blue)** by querying the log/alert store — scored per technique **detected or not**, on a recurring cadence, so it catches **security drift** (the detection that worked last quarter and silently broke). **Placement decided (2026-08-20): it homes in the `penetration-testing` plugin, not `security-governance`** — the load-bearing reason is that its red half `atomic-simulation` **executes real ATT&CK techniques against a live environment**, so it is bound by the §5 full-kill-chain safety model (committed engagement scope file, `#volatile` expiring authorization, no DoS ever, lab-default with production a separate louder sign-off, per-act opt-in, action log, cleanup verification, mid-run abort) — exactly the machinery `penetration-testing` already owns and every skill there opens with. Folding it into `security-governance` would contradict Stage 5's explicit decision that a blue-team/GRC install must **not** carry offensive execution. The author→validate→roll-up loop still closes cleanly **across** plugins by named handoff — the same cross-plugin author/test fence the library already uses for the CSP (govern authors, qa tests). **Two language-agnostic skills** (`security/<skill>/`, prefix `purpleteam-*` — a lane prefix bundled into the host plugin, the `design-*`/`observability-*` precedent): `atomic-simulation` (the **red half** — **Atomic Red Team** via `invoke-atomicredteam` (module v2.3.0; pin the atomics-folder commit for reproducibility) · **Apache Caldera 5.3.0** (note the governance move — the repo relocated `mitre/caldera` → `apache/caldera`) for technique *chains* · **Stratus Red Team v2.32.1** for cloud/K8s atomics · **VECTR CE ce-9.14.1** as the coverage/drift scoreboard; every technique detonated, logged, then **cleaned up and verified**; §5-gated because it executes) · `detection-validation` (the **blue half** — for each simulated technique, assert the control fired by querying the log/alert store within the detonation window, **sigma-cli 3.1.0**-converted queries + LogQL/PromQL/KQL/SPL; the **four outcome tiers** *Blocked · Alerted · Logged-only · No-signal* distinguish a **rule gap** (→ `secgov-detection-engineering`) from a **telemetry gap** (→ `observability-engineer-*`); read-only, no offensive gate). **The agent — `purple-team-engineer`** (`security/agents/purple-team-engineer.md`, command `/purple-team-engineer`): four steps — **0 Rules-of-engagement, scope & telemetry gate *(blocking)* → 1 Plan the technique set (map each ATT&CK id to the detection it validates) → 2 Simulate → validate (the purple pair, per technique) → 3 Report + drift + cleanup verification.** Modes **NEW / REVALIDATE** (the scheduled re-run: each technique re-simulated fresh and prefixed **Still detected / Newly detected / Regressed (drift) / Still not detected** — *Regressed* is the highest-signal finding). Spine **MITRE ATT&CK Enterprise v19 (pinned)**; the report gate is **detected/not-detected by outcome tier, not CVSS** — the deliberate divergence from `penetration-tester`'s CVSS impact score, because a validation proves whether a control *works*, not how bad a vuln is. Loads only the two purple skills + `pentest-reporting` + the always-on `ep-*`; **never fixes** (a rule gap → `secgov-detection-engineering`; a telemetry gap → `observability-engineer-*`; a vulnerable app → `be-*`/`fe-*`/`devops-engineer`; it **revalidates** after). Saves `docs/security/<NNN>-purpleteam-r<N>.md`. It **closes the author→validate→roll-up loop**: `secgov-detection-engineering` authors the detection → `purple-team-engineer` validates it fires → `security-architect` rolls the validated coverage into the posture picture. **Fences:** vs **`penetration-tester`** — it *exploits* to prove *impact* (CVSS, once per engagement); purple *simulates known atomics* to prove *detection* (detected/not, scheduled); shared ATT&CK Enterprise spine + the same §5 gate. vs **`secgov-detection-engineering`** — it *authors* the rule; purple *validates* it fires (author there, validate here). vs the **observability lane** (`observability-engineer-*` + `queries`/`dashboards`, named peers) — that **owns the telemetry substrate** (Loki/Prometheus/Tempo, Alertmanager, the log pipeline); purple **authors the security assertions over it**, and a `No-signal` result or a failed telemetry gate is a handoff to them.

**Offensive-lane fences.** vs **`qa-security`** — that detects, weights (reachability), and proves a *single* vuln fires on an authorized env (its `exploit-validation`), stopping at single-vuln proof; this takes that proof to a **foothold and the full chain**. vs **`infra-security-tester`** — that runs infra *posture* benchmarks + bounded active probing mapped to ATT&CK Cloud/Containers; this runs the offensive host/app kill chain mapped to ATT&CK Enterprise. vs **`exploit-validation`** (the Stage-2 skill specifically) — single-vuln-proof-on-one-app (theirs) is the feedstock; foothold-and-kill-chain (ours) is the consumer; the two never overlap because the boundary is altitude and goal. vs the **fix agents** — this lane finds and retests, never remediates. LLM red-teaming stays in `qa-llm-*`; social-engineering/physical are out of scope.

**The defensive/governance lane — `security-governance`** (Stage 5, applied 2026-08-20): the blue-team + CISO-altitude half a security program needs, the counterpart to the offensive lane. **Four language-agnostic skills** (`security/<skill>/`, prefix `secgov-*`, self-contained, **agent-reached — no command**; Read-only; **`security-architect` applies the fixes** in a separate run (the swept artifacts sit inside its own `docs/security/**` + `detections/**` write fence), with wiring routed to `fe-*`/`be-*`/`devops-engineer`, telemetry gaps to `observability-engineer-*`, and "authored but not validated" to `purple-team-engineer`. Report: `docs/audits/<NNN>-security-governance-conformance-r<N>.md`.

**Why `penetration-testing` has no self-audit** (decided 2026-08-20, reversing only the *deferral*, not this): its outputs are **per-engagement reports and scope files — point-in-time records, not standing artifacts that drift**, so a sweep months later produces findings nobody can act on (an action log cannot be written retroactively; cleanup cannot be re-verified after the environment moved on). Its rules are enforced as **blocking pre-conditions** — the §5 gates the agent runs before and between every step, plus `pentest-reporting`'s mandatory sections — so a post-hoc sweep finds only what the gates already refused to allow. And the artifacts exist only in a repo that already ran an engagement, where `security-architect` reads them as lane input anyway. This restates `SECURITY-EXPANSION-PLAN.md` §4's standing decision that offensive lanes **do not** ride the conformance engine because they produce *proof*, not conformance findings. The one residual the runtime gates cannot cover — sensitive material that reached a **committed** file — is **section M** of the governance checklist, which sweeps `docs/security/**` and `detections/**` whoever authored them; only the redaction rule crosses that boundary, and the offensive findings themselves are never re-verdicted there.

**Governance-lane fences.** vs **`security-test-planner`** — the planner runs **before** the assessment to sequence which lanes touch a platform; `security-architect` runs **after** to roll their findings into posture. Two ends of one program; neither does the other's job. vs the **lane agents** (`qa-security`, `infra-security-tester`, `penetration-tester`, `purple-team-engineer`) — they *produce* findings under their own gates; the architect *consumes* and normalizes, running no scan itself. vs **`qa-security`** on the skill split — its `client-side-security` *tests* the CSP that `security-hardening` *authors*; its `secrets-scan` *detects* the secret that `secrets-hardening` *rotates*. vs the **fix agents** — the architect prescribes and authors the language-agnostic security artifact, routing app/infra *wiring* to `fe-*`/`be-*`/`devops-engineer`; it never edits the codebase. vs **`purple-team-engineer`** (`penetration-testing` plugin) — `detection-engineering` *authors* the detection, purple-team *validates* it fires.

New-project setup = copy `security/` (13 skills + 4 agents) — or install the offensive + purple **`penetration-testing`** plugin (7 kill-chain skills + 2 purple-team skills + `penetration-tester` + `security-test-planner` + `purple-team-engineer`) and/or the defensive **`security-governance`** plugin (4 `secgov-*` skills + `security-architect`); both bundle the two always-on `ep-*`.

## Engineering-practices catalog

The `engineering-practices/` folder is the **developer-workflow spine** — the language-agnostic idea → spec → plan → execute → verify → finish loop that sits *beside* the `qa/` and `frontend/` domains rather than inside them. The 14 in-scope skills (the 12 workflow skills adapted from obra/superpowers, self-contained: they reference only each other — plus the 2 audit skills) and the domain's one agent (`code-auditor` — the deliberate exception to "skills-only") are **bundled into every stack plugin** (the eight `qa-*` / `fe-*` / `be-*` plugins) — no standalone plugin. All skills use the `ep-*` name prefix.

**The chain** (each skill announces itself and hands to the next):
- `ep-brainstorming` — turn an ad-hoc idea into an approved design/spec (`docs/specs/NNN-<topic>-design.md`, written on the current branch); HARD-GATE before any code. **Scoped:** a step-by-step agent with its own design gate (`fe-blazor`, the `qa-*` orchestrators) already satisfies the gate — do not run this on top of them. Its browser **visual companion** is opt-in on explicit request only. → `ep-writing-plans`
- `ep-writing-plans` — approved spec → detailed bite-sized implementation plan (`docs/plans/NNN-<feature>.md`, written on the current branch): **one flat, ordered list of tasks** `T1…Tn` (never phases, never slices), each with a stated **`Deliverable`** and its `Depends on`, ordered so every task is startable at its position and the tree builds and tests green at every task boundary; a header task table indexes the order and the deliverables; one action per step inside a task, complete code in every step. → `ep-executing-plans`
- `ep-executing-plans` — execute a written plan task-by-task **in the plan's order**, confirming each task's stated `Deliverable` actually exists before it counts as done, reporting at a checkpoint after each task (task list via TaskCreate/TaskUpdate); stops when blocked. The inline execution path; `ep-delegate-to-subagents` runs the same tasks through subagents. → `ep-finish-branch`
- `ep-finish-branch` — tests-pass gate → structured merge/PR/keep/discard options → provenance-based worktree cleanup.

**Cross-cutting** (entered anytime, not part of the linear chain):
- `ep-test-driven-development` — the dev-side red-green-refactor **inner loop**. Complements `qa/` (which owns suite architecture, page objects, builders); this owns only the loop. Reconciles with the CLAUDE.md test rules — no conflict (per "skill wins for its domain", both agree).
- `ep-systematic-debugging` — root-cause-first, four-step debugging; writes the failing test via `ep-test-driven-development`, confirms via `ep-verify-before-done`.
- `ep-verify-before-done` — evidence-before-claims gate before any "done/fixed/passing" statement or commit/PR. Reinforces the global "report outcomes faithfully" rule.
- `ep-worktrees` — isolated-workspace setup; prefers the harness's native worktree tool (`EnterWorktree`) over the git fallback.
- **`ep-agent-orientation-cache`** — the **agent-memory protocol every agent in the library loads on every run** (the only `ep-*` skill that is not opt-in, and the only one shipped in **all fourteen** plugins — including `data`, `business-analysis`, and `training-data`). An agent's orientation pass — version lane, build/run commands, layout, and the inventory of reusable seams — is identical across runs of that agent type and changes rarely, so it is persisted to **`docs/agent-context/<agent-name>.md`** in the target project (one file per agent *type*), then **read-validated** rather than re-derived. The gate: no file / not a git repo / baseline commit not in history / older than 30 days → **FULL**; `HEAD` == baseline and clean tree → **TRUST**; otherwise a **DELTA** pass where a changed fingerprint file (manifest, lockfile, build config) invalidates the version lane and everything keyed to it, and other changed paths invalidate only their own section. **Three things are never cached:** green-on-arrival (working-tree state, not layout), `#volatile` live-resource facts (`data-architect`'s server probe, `devops-*` cloud reads, the API a `qa-*` suite asserts against), and any file the map names that the run is about to edit — **the map is a lead, not evidence**. **Update-after** closes every run: correct what the run disproved, add the seams the run *created*, re-stamp baseline + fingerprint, prepend one session-log line. **The fence:** it records what the code **is** — never findings (`docs/audits/`), plans (`docs/plans/`), specs (`docs/specs/`), or business model (`docs/business-model/`). The read-only auditors (`code-auditor`, `devops-auditor`) cache the audit *spine* only; a `file:line` in a finding is still only ever produced by reading that line this round. The skill is the engine; each agent supplies its own field list — same split as `ep-standards-audit-engine`. Rollout: `AGENT-ORIENTATION-CACHE-PLAN.md`.
- **`ep-code-comments`** — the **comment discipline every code-writing and code-reviewing skill applies**, and the second `ep-*` skill shipped in **all fourteen** plugins. The rule: **no inline comments**; the only permitted comment is a short doc comment on a method/class/type, **only where the name genuinely cannot carry the meaning**, and **only on a complex flow** — which is pinned to exactly four qualifying cases (a non-obvious business rule or invariant the code enforces but does not state · an ordering/concurrency/lifetime constraint a caller must respect · a deliberate deviation from the obvious implementation, with its reason · a public API contract the signature can't express). Everything else — properties, DTOs, getters, assign-only constructors, single-expression methods, obvious overrides — gets nothing, and a doc comment restating the signature is deleted. **A stale comment is worse than none:** it is the defect, and deletion is the fix. **Directives are not comments** (suppressions, pragmas, serializer/OpenAPI annotations, `'use client'`, source-generator markers) — they stay, but a suppression must carry its reason; likewise **database object comments** (`COMMENT ON`, extended properties) are schema metadata, not source comments. **Test code** adds one thing: the test name and the AAA shape *are* the explanation, `// Arrange`/`// Act`/`// Assert` banners are the most common violation, and exactly **three** comments are permitted — a linked defect id, a recorded instructed deviation, and the source of a domain-fixed magic value. **Review grading:** an inline comment is `minor`; a comment that is wrong, or that exists because the code is unclear, is `major` — and the fix is the rename or the extraction, never a reword. **Audit reporting:** "no inline comments" is **one finding family** (count + 3–5 cited sites + one fix direction), while **each stale comment is its own finding**. The skill is the engine; each loader supplies its language's doc-comment and suppression syntax plus its one corollary — same split as `ep-standards-audit-engine`. Loaded (never routed to) by the 6 `code-review` reviewers, the 9 qa test reviewers, the 3 `standards-audit` checklists, and **31 code-writing agents** on the same always-on footing as `ep-agent-orientation-cache`. Documentation artifacts (`docs/plans`, `docs/specs`, `docs/business-model`, `docs/audits`) are explicitly out of scope.

**Agent-dispatch:**
- `ep-delegate-to-subagents` — execute a plan by delegating self-contained tasks to subagents; the alternative to running the same plan inline with `ep-executing-plans`. Flow is 1 implementer subagent per task + controller review (spec then quality, CLAUDE.md severity-table format), with dedicated reviewer subagents available per task.
- `ep-parallel-agents` — fan genuinely independent problems out to concurrent agents, one per independent domain; say what you are spawning and why rather than fanning out silently.

**Code review (the request/receive pair, entered around finishing & subagent-driven work):**
- `ep-requesting-code-review` — get a completed change reviewed before it cascades, via the **native review command** (e.g. `/code-review`), a **self-review** against the controller rubric, or a **reviewer subagent**. Carries the `code-reviewer.md` prompt template; findings in the CLAUDE.md severity table. Named by `ep-finish-branch` (before merge/PR) and `ep-delegate-to-subagents` (its per-task review).
- `ep-receiving-code-review` — the receiving half: verify feedback before implementing, fix by severity (blocker → nit), push back with technical reasoning, no performative agreement.

**Audit (read-only analysis of existing code — the `code-auditor` agent at `engineering-practices/agents/code-auditor.md` owns both, stack-agnostic, static-first with execute-opt-in evidence). Every run is one of two modes × one of two lanes:**
- **Mode A — BASELINE** (first audit: build the stable spine, verdict everything, save Round 1) · **Mode B — RE-AUDIT** (reload the spine, re-trace every item **fresh**, prefix each **Resolved / Resolved (differently) / Still open / Still open (regressed) / New**, save Round N). **EXTEND** (new stories/surfaces) is a Mode A variant that appends with the next free IDs, never renumbering. Artifacts live in `docs/audits/`: `…-requirements.md` (append-only register) + one `…-audit-r<N>.md` per round — rounds are never overwritten, IDs never reused, so the trend ("12 open at r1 → 4 at r2") is real.
- `ep-spec-vs-code-audit` (**SPEC lane** — a spec, *or a set of stories/ACs/tickets*) — Mode A's first act is **consolidation**: merge the sources into one deduped, **lettered-section**, ID-stable requirement register and **save it before reading any product code** (same source stated twice → one entry, two citations; sources contradicting → a paired `⚠️ CONFLICT`, both verdicted, owner decides). Then per-requirement verdicts **Met / Partial / Missing / Divergent / Unverifiable** with `file:line` evidence (`#confirmed`/`#inferred`; negative claims name the search) → coverage metrics + severity-tabled findings split into **Data issues / Code issues / Logical conflicts**. Loads `qa/manual/requirements-breakdown` (loaded-not-owned, bundled into all eight stack plugins) to distill raw-prose sources first. `Divergent` always escalates to the owner — the auditor never picks spec vs code.
- `ep-feature-audit` (**FEATURE lane** — a feature/area by name, no spec) — declared scope + **driving question** → lettered surface decomposition (the report *is* the register here) → three inventories (functionality narrative · **validations & gates** · integration map with per-boundary trust assumptions) → findings, each = mechanism + concrete failure scenario/impact band + severity + fix direction, grouped into **defect families** → priority table (split **Data issues / Code issues / Logical conflicts**) + **leverage-ordered** recommended sequencing. Mode B re-traces each finding then **sweeps its defect family** (a fix at one site routinely misses siblings). The report is a first-class test-basis input for `qa/manual/requirements-breakdown` (finding boundary conditions are BVA seeds).
- **Every section/surface closes with a rollup summary** — one per section, never per item, 2–4 sentences of *judgment* (state · pattern · next action), distinct from the arithmetic Movement/metrics block. **Resolved is only claimed after re-reading the code that round** — commits, ticket status, and green tests are leads, never evidence.
- **Findings are classed** — every finding sits under exactly one of **Data issues** (the code is right, the data it runs on is wrong — seed/reference rows, config values, migration residue, invariant-violating state; a data/platform owner acts) / **Code issues** (the logic is absent, incomplete, or wrong; the stack agent acts) / **Logical conflicts** (two things that cannot both hold — a `⚠️ CONFLICT` pair, a `Divergent` verdict, contradictory code paths; an owner **decides**, the auditor never picks a side). All three headings appear in every round (`None.` when empty) so rounds compare class by class; class is orthogonal to severity and to defect family.
- **Fences:** never fixes (the owning `be-*`/`fe-*` agent applies remediation); security *attacks* belong to `qa-security` (the audit's gates inventory is its starting map); spec-vs-spec conflicts belong to `business-analyst`; pre-implementation story audits belong to `ba-story-quality-review`.

**The third lane — CONVENTION** (`engineering-practices/standards-audit-engine` → `ep-standards-audit-engine`, the **engine only**): where the SPEC lane's spine is a register built from *the user's* sources and the FEATURE lane's is a surface decomposition, this lane's rule set is **a plugin's own conventions**, swept across the whole codebase. The engine is stack-agnostic and carries no rules — Mode A/B rounds, the `docs/audits/<NNN>-<plugin>-conformance-r<N>.md` artifact contract, evidence rules, severity semantics, grouping/coverage policy, the 5 steps (version gate → applicability matrix → sweep → report → hostile self-review), and the shared report templates. Each stack supplies the rules through its own `standards-audit` skill (`fe-react-standards-audit`, `be-dotnet-standards-audit`, `qa-dotnet-standards-audit`, and — outside the plan's original scope — `secgov-standards-audit`; the rest per `CONFORMANCE-AUDIT-PLAN.md`), which owns the lettered sections, the version-lane probes, and the applicability probes. **One exception:** `devops-auditor` is an *agent* that supplies its own twelve sections directly — devops is out of the conformance plan's scope, and its "which rules apply" question is answered by the same tool-stack confirmation gate its `devops-engineer` sibling runs, so a separate skill would only add a hop. `security-governance` joined the lane in 2026-08 and took the **skill** shape rather than devops's agent shape — its applicability is answered by static probes with no one-of-N tool family to anchor on, so the confirmation gate that justifies the agent container has nothing to gate. Its version lane is also the lane's first non-code one: a **standards-and-tooling pin lane** (ATT&CK · Sigma tooling · CRS · OWASP Top 10 · ASVS/PCI/ISO/SOC 2 editions) where an older-but-supported pin is a *deviation* and a withdrawn edition is a finding, and where **absence of a control is a coverage note routed to `security-architect`, never a conformance finding**. **The engine is loaded, never invoked** — its description forbids direct routing, since an audit run from it alone would have no rules to check against. Entry point per stack: `/<plugin>-audit`. Fence against the sibling lanes: a **stack reviewer** skill handles one diff inline with no artifact; **this lane** sweeps the repo against fixed plugin rules and persists rounds; the **`code-auditor` agent** owns code-vs-spec and spec-less feature traces across any stack. The engine ships in **all ten** `qa-*` / `fe-*` / `be-*` / `devops` plugins as of 2026-07-26, and in `security-governance` as of 2026-08-20 — including those whose stack audit is not authored yet, where it sits inert (its description forbids direct routing) so no wiring step remains when the audit lands. `fe-react` still carries its own procedure copy until the extraction lands (Step 1 of the plan) — a known temporary duplication, not a second engine.

**Reconciliation with global rules:** where a process skill and a global rule touch — `ep-test-driven-development` vs the Test code rules, the `ep-brainstorming` HARD-GATE vs the numbered-agent design steps, `ep-verify-before-done` vs "report outcomes faithfully" — the existing "skill wins for its domain" rule already governs; the skills are written to agree with the global rules, so no override is triggered in practice.

## Business-analysis catalog

The `business-analysis/` folder is the **upstream requirements domain**, organized in **two lanes** and shipped as the self-contained `business-analysis` plugin. The **authoring lane** turns a vague stakeholder ask into refinement-ready artifacts (scoping writeup → epics → INVEST stories, plus a review-only backlog audit). The **reasoning lane** is the cross-feature business-flow layer — it sits *upstream* of `qa/manual/` (which distills one feature for testing) and owns what nothing else does: detecting conflicts **between features** and keeping a **persistent per-project business model** so later sessions reason with whole-project context. Language-agnostic skills + one step-by-step orchestrator agent per lane. (The pure-communication skills — `stakeholder-updates`, `meeting-notes`, `incident-postmortem` — stayed in `communication/`, which remains under construction.)

**The KB (`docs/business-model/` in the target project)** — versioned, diffable, Cline-Memory-Bank-shaped: `INDEX.md` (read first, every session) · `glossary.md` · `flows/` · `entities/` · `decisions/` · `interaction-map.md` (resolved conflicts + rationale) · `active-context.md` (dynamic tier). Contract: **read-first / update-after**; stable IDs (`FLOW-`/`ENT-`/`DEC-`/`CONF-`) + source traceability; annotation grammar `[TBD - reason]` · `⚠️ Assumption:` · `#confirmed`/`#inferred`/`#observed`.

**Authoring-lane skills** (`business-analysis/skills/`, `ba-*`):
- `ba-scoping-writeup` — vague business problem / stakeholder ask → structured single-initiative scoping writeup (problem statement, goals + measurable success metrics, stakeholder map, in/out/deferred scope, constraints, likelihood×impact risks, assumptions, open questions); includes the elicitation question bank for driving discovery
- `ba-epic-writer` — scoped writeup → one or more epics, each with a one-sentence WHO / DO WHAT / SO THAT MEASURABLE outcome, a named slicing strategy, anticipated child stories, explicit out-of-scope, epic-level DoD; sizing heuristics (story set vs epic vs program)
- `ba-story-writer` — scoped requirement / epic → INVEST user stories with Gherkin AC (one behavior per scenario), functional vs non-functional AC separated, story-level out-of-scope + dependencies
- `ba-story-quality-review` — review-only readiness audit of stories/epics **authored elsewhere** (client, another team, a PO): INVEST + AC quality + testability + backlog hygiene checks, per-story verdicts, severity-tabled findings; never rewrites — routes fixes to `ba-story-writer` / `ba-epic-writer`

**Reasoning-lane skills** (`business-analysis/skills/`, `ba-*`):
- `ba-project-memory` — the KB protocol every reasoning-lane skill loads (layout, contract, authoring rules, init)
- `ba-process-flow-diagram` — requirements → BPMN-disciplined Mermaid flow (named actors/swimlanes, every decision exit incl. failure labeled, boundary events, precondition→action→postcondition steps, event-timeline pass)
- `ba-entity-state-grid` — **one state × event grid per business entity**, all features overlaid, transitions annotated with owning feature; conflict surfaces: double-fire, state interference, orphan transitions, silent `—` assumptions
- `ba-decision-table` — **one merged decision table per shared decision point** with a declared DMN hit policy (U/A/F/P/C); completeness check = gaps, overlap check = contradictions, missing Collect operator = missing stacking rule; precedence is a *business decision to escalate, never invent*
- `ba-feature-conflict-check` — the quality gate: normalize the new feature into trigger/actor/action/data/constraint/state tuples → pairwise sweep against the KB with the **11-class conflict taxonomy** (contradictory rules · trigger overlap · state interference · resource contention · ordering/race · circular dependency · policy stacking · permission/authority · duplication/subsumption · terminology drift · boundary divergence) → **every finding gets a concrete boundary condition** → severity table; resolutions recorded in `interaction-map.md`

**Agents** — one per lane, peers that name each other:
- `business-analysis/agents/requirements-author`: the authoring lane. Five input modes (raw ask / scoped writeup / epics-provided / stories-authored-elsewhere), four steps (Initiative scoping → Epic shaping → Story refinement → Backlog audit 3R on-demand). Loads **only** the four authoring-lane skills; reuses the KB's glossary/IDs when one exists but never edits it. Downstream defaults: `business-analyst` sweep when stories touch shared rules, then `qa/manual/requirements-breakdown` / `qa-test-case-designer`.
- `business-analysis/agents/business-analyst`: the reasoning lane. Three modes (analyze / model / audit), six steps (Orient → Normalize → Model per selection matrix → Sweep → Resolve & persist → Report). Loads **only** `business-analysis/*` skills. **Brownfield-capable** like every agent in the library: on a populated KB it orients (KB inventory + staleness signals), then fixes (source-changed vs model-defect vs unresolved-conflict triage — never invents precedence) or extends (folds a new feature into the existing model, reusing stable IDs and glossary) with a `Mode: FIX | EXTEND` KB-delta report; the discipline is inlined since this plugin doesn't bundle `ep-*`.

**Scope fence vs `qa/manual/*`:** `requirements-breakdown` keeps single-story distillation; `test-design-techniques` keeps decision-/state-table *test-design mechanics* (rule coverage, n-switch); this domain owns requirements authoring + the cross-feature models + the sweep and **never produces test cases**. The three document-ingestion altitudes fence each other explicitly: `ba-scoping-writeup` (one initiative, for scoping) · `ba-feature-conflict-check` (cross-feature, against the KB) · `qa/manual/requirements-breakdown` (one doc, for testing). Handshakes: story sets are the sweep's normalization input; KB artifacts are first-class test-basis inputs; sweep boundary conditions are BVA seeds; `qa-test-case-designer` names `business-analyst` as the upstream peer.

New-project setup = copy `business-analysis/` (all 9 skills + both agents).

## Training-data catalog

The `training-data/` folder is the **LLM/VLM training-data engineering** domain — building the datasets a *small* language or vision-language model trains on, distinct from `ai-development/` (which builds apps *on top of* a hosted model) and from `qa/`'s `ai-feature-testing` (which *tests* a model's behavior). Organized like the rest of the library — domain-encapsulated, numbered orchestrator agent, one marketplace plugin (`training-data`) — it covers **all four training stages** (pretraining corpus · instruction/SFT · preference/DPO · evaluation) across **both modalities** (text and image-text / VLM), by **curation and/or teacher-model synthesis** (equal-weight lanes). Skill names carry the `td-*` prefix.

**Skill shapes.** Two, like the rest of the library:
- **Cross-stage `_shared/`** (`training-data/_shared/td-*`) — the three foundations every stage uses: `td-dataset-formats` (the on-disk contract — JSONL one-example-per-line, the record envelope `id`/`source`/`license`/`created_at`, the OpenAI `messages` shape, the VLM image-as-typed-part rule, splits/sharding, the mandatory dataset card; **loaded on every run**) · `td-data-quality` (the non-negotiable quality gate — normalize → filter → exact-dedup → near-dedup (MinHash/LSH) → quality-filter → split → **decontaminate-last** against the eval targets; PII/secret scrubbing; balancing/mixing; **run on every dataset before it ships**) · `td-synthetic-generation` (the teacher-model engine — seed-grid diversity → self-instruct/evol-instruct expansion → **pinned+calibrated LLM-judge** grading → dedup/decontam handoff → stage format; loads `ai-development/claude-api` for the API mechanics; every synthetic record flagged `synthetic:<model-id>` + `synthetic-review-required`).
- **Stage skills** (`training-data/skills/td-*`) — `td-pretraining-corpus` (collect → extract HTML/PDF → clean → dedup (document + substring) → quality-filter → shard; token-budget sized to the model; documented mixing blend) · `td-instruction-sft` (task-taxonomy-first chat/instruction data, curate + synthesize blended, tool-use traces validated against the tool schema, assistant-turn-only targets) · `td-preference-data` (DPO/ORPO/KTO pairs; the **margin rule** — `rejected` is plausibly-worse not garbage, ties dropped, length-bias controlled; **on-policy** sampling from the student) · `td-eval-sets` (frozen, isolated, canary-seeded held-out evals; deterministic scoring preferred, LLM-judge pinned+calibrated; per-capability coverage) · `td-vision-language-data` (the multimodal extension across *all* stages — captioning/VQA/OCR/grounding/multi-image, image content-hash + pHash dedup, **image decontamination**, one stated bbox coordinate convention, CLIP-alignment filtering, EXIF/PII strip).

**Agents** — two, a build/verify pair:
- **`dataset-engineer`** (`training-data/agents/dataset-engineer.md`, command `/dataset-engineer`) — the step-by-step builder: **1 Spec** (target model + tokenizer, stage, modality, sourcing, eval targets, composition goal, license posture) → **2 Source/curate** → **3 Synthesize** (generate-small → validate → cost-estimate → scale) → **4 Quality gate** (`td-data-quality`, **decontamination-last, always**) → **5 Format & split** (JSONL, split by dedup cluster, shard, manifest) → **6 Card & review**. Loads **only** `training-data/*` skills (+ `ai-development/claude-api` when synthesizing, + the two always-on `ep-*`); **NEW** and **EXTEND/FIX** modes (brownfield-capable — orient on the existing manifest/card, re-verify the `#volatile` contamination status *this session*, re-enter only the touched steps). Datasets land in `datasets/<name>/`; cards in `docs/datasets/`.
- **`dataset-auditor`** (`training-data/agents/dataset-auditor.md`, command `/dataset-auditor`) — the **read-only** audit of an existing dataset, `Write`/`Edit` reaching only the report under `docs/datasets/audits/`. Eight sections **A–H** (format validity · **contamination** · duplication · PII/secrets · license & provenance · composition & coverage · split integrity · card & manifest), each naming the skill whose rules it enforces, scored on the `CLAUDE.md` severity table with `id`/`file:line` evidence read this round. **Re-runs the contamination and dedup checks itself** — the dataset card is a claim under audit, not the source of truth. Mode A **BASELINE** / Mode B **RE-AUDIT** rounds via the loaded `ep-standards-audit-engine`; **fixes nothing** — `dataset-engineer` applies every finding. The two domain invariants — **contamination-last (B)** and **license coverage (E)** — are blocker-class by default.

**The two invariants every dataset holds:** **decontamination runs last and always** (no dataset is shippable, and no eval number trustworthy, until the train split has been checked against its eval targets — the teacher model is itself a prime contamination source), and **synthetic data is a flagged draft, never verified truth** (`synthetic:<exact-model-id>` + `synthetic-review-required`, the teacher's terms of use respected and recorded).

**Fences.** vs **`ai-development/claude-api`** — that builds apps that *call* a hosted model; this builds the data to *train* a model, and *loads* the claude-api skill only for the synthesis mechanics. vs **`qa-llm-{stack}` / `ai-feature-testing` / `ai-answer-quality-testing`** — those **run** the eval and score the model (harness, stochastic pass-rate, RAG triad, OWASP-LLM red-teaming); `td-eval-sets` **builds the eval data** they run, then hands off. vs **`data-architect`** — that owns the *application* database; if a corpus or dataset must be stored/queried at scale (a vector store, a warehouse), that storage design is its, the dataset *content* is this domain's. **Out of scope:** training/fine-tuning the model itself, and the training harness.

New-project setup = copy `training-data/` (all 8 skills + both agents), or install the `training-data` plugin.

## Tooling catalog

The `tooling/` folder is the **agent-drivable-surface** domain — turning a project, or a chosen set of its functionalities, into something an agent (or a script, or a CI step) can drive **correctly on the first call**. Domain-encapsulated, one orchestrator agent, one marketplace plugin (`tooling`). Skill names carry the `tool-*` prefix.

**The domain's one rule: contract first, code second.** An MCP server and a CLI are the same capability set in two renderings, so the design happens once, in a reviewable document, and both surfaces are rendered from it mechanically. Building straight from a prose description is what produces an `execute(command: string)` tool, untyped payloads, and forty tools nobody can compose.

**Skills** — one shared contract skill, two builders:
- **`tool-capability-contract`** (`tooling/_shared/capability-contract`) — derives the surface from the codebase's entry points (route tables, application services, existing CLI/script entry points, job consumers, enums and validation attributes, config binding) and writes `docs/specs/<NNN>-<surface>-tool-contract.md`: the **capability table** (`<noun>.<verb>` id · intent · kind `read`/`write`/`destructive` · `file:line` source · auth · idempotency · flow), a **typed contract block** per capability (inputs with constraints *and an example* · output shape · an error table whose last column is *what the caller does next*), the **flows** (the ordered sequences, naming the field that carries between steps and the recovery for the likely failure), and the **dependency + trust boundary** section (config vs secrets, what is deliberately not exposed). Its `references/output-contract.md` fixes what both builders implement literally — the `{ok,data,meta}` / `{ok,error}` envelope, the **eight-code closed error vocabulary** with a stated `retryable`, mandatory clamped paging with `hasMore`, a ~25 KB per-response token budget, and the wire types (ISO-8601 UTC · integer minor units · string ids · enumerated enums). `references/example-contract.md` is the filled golden example.
- **`tool-mcp-builder`** (`tooling/skills/mcp-builder`) — renders each capability as one MCP tool: name from the capability id, the intent sentence as a three-line routing description, the inputs table as a Zod/typed schema with `.describe()` + example per field, `outputSchema` + `structuredContent`, annotations set from `Kind`, and a `confirm: z.literal(true)` gate on every destructive capability. **Lane table:** in-process TypeScript (Node projects) · TypeScript sidecar (any stack with an HTTP API — the default) · stack-native `ModelContextProtocol` / Spring AI MCP **only** when the capabilities are in-process and unreachable otherwise. `references/typescript.md` · `references/stack-native.md`.
- **`tool-cli-builder`** (`tooling/skills/cli-builder`) — renders each capability as `<bin> <noun> <verb>` with kebab-case flags, **two renderings of one object** (`--json` emits the envelope; text mode is derived from it), stdout reserved for results with every diagnostic on stderr, a **documented exit-code table** mapped from the error vocabulary (`2` validation · `3` not-found · `4` conflict · `5` forbidden · `6` retryable), flag→env→file→default config precedence with secrets never a flag, and `--dry-run` + a TTY-gated confirmation on every destructive command. Unlike MCP, the CLI **matches the project's stack**: `commander` · `System.CommandLine` (`dotnet tool`) · picocli. `references/typescript.md` · `references/stack-native.md`.

**Agent** — **`tooling-engineer`** (`tooling/agents/tooling-engineer.md`, command `/tooling-engineer`): **1 Contract** (confirmed with the user before any code) → **2 Lane** (from the detected stack; installed SDK version confirmed against *its* docs, never memory) → **3 Build** → **4 Verify** (every capability called with the contract's examples, one full flow proven output-into-input, one validation failure and one conflict proven actionable, the destructive gate proven to refuse) → **5 Ship** (registration/install block, tool table, flows as literal invocations) → **6 Review**. Brownfield-capable — orients on the existing surface's prefix, envelope, paging style, and installed SDK version (`#volatile`), then specs only the delta and inherits the existing conventions without exception. Loads **only** `tooling/*` plus the two always-on `ep-*`.

**Deliberately not built:** flows are **not** collapsed into a mega-tool or a composite command. They live in tool descriptions ("ids from here go to X") and in the README as literal invocations, because the point of the surface is that each step's output feeds the next visibly. A composite is justified only when the steps are atomic, and the reason goes in the code's one permitted doc comment.

**Fences.** vs the vendor **`ai-development/mcp-builder`** — that wraps a **third-party HTTP API with no local codebase** and owns the eval-question harness; this one derives from a **codebase** you control. vs **`be-shared-api-surface-plan`** — that designs the REST API for human/browser clients; this domain *consumes* its output as a Step-1 input and never designs APIs. vs **`be-documenter`/`be-feature-documenter`** — their feature traces are excellent Step-1 input, but they document for people. vs **`devops-engineer`** — it owns pipelines; this domain builds the tool a pipeline step calls. **Hard fence:** the surface adapts to the project, never the reverse — adding an HTTP API so a sidecar becomes possible is out of scope unless independently justified.

New-project setup = copy `tooling/` (3 skills + the agent), or install the `tooling` plugin.
