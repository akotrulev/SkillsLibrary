# Reconcile procedure — detail

Loaded by `SKILL.md` when a run finds an existing guide. The numbers are the procedure's own; `SKILL.md` carries each step's one-line rule.

## 1. Fold the answers

The first act of the run, before anything else is written. For each *Open questions* row whose *Answer* is filled:

1. Write the answer into the body where the rule is stated, as one plain sentence (the reason, or the confirmed policy), and into *Rules and limits* when it changes a row. It is a sentence like any other — no strike-through, no note that it was asked.
2. Remove the row. Its id is spent and never reused.
3. Count it in the report (`Answers folded: <n>`). In a KB run, list it for `business-analyst`, who decides whether a model row is promoted to `#confirmed`; you never write `#confirmed`.
4. An answer the code contradicts is **not** folded: the row stays with its answer, and the report escalates both readings — the answer, and what the product does — for `code-auditor`.

## 2. Check staleness

Read the `source:` sha of the guide's stamp comment (a guide not yet moved to the stamp: its `Derived from` or `Generated by` line), compare it with `HEAD` and the git delta for the area's paths, and report whether it is stale.

## 3. Existing documentation is updated in place

Never deleted and regenerated, never rewritten from a fresh trace and compared.

1. **Same file, same history.** The guide is edited. `Created` is kept, a `Last updated` line is added, and `~~old~~ → new` marks every changed fact.
2. **A guide in the previous shape** (tasks that hold formulas, `## Related areas`, `**Trigger:**` / `**Result:**` automatic work, visible `**Id:**` / `**Owned by:**` / `**Derived from:**` / `**Generated by` / `**Models:**` / `**Audience:**` lines) is brought into the current shape in the same file, with the same `Created` and every fact kept:
   - it gains `## In short`;
   - each formula moves from its task to `## How it is calculated`; the task's outcome says the result in one sentence and the `**Example**` stays put;
   - `## Related areas` becomes `## See also`, rewritten to the plain list;
   - automatic work is rewritten to `**When:**` and `**What people notice**`;
   - the About lines move into the stamp comment, `**Id:**`, `**Owned by:**` and `**Models:**` among them;
   - `## Rules and limits` gains the `Where you meet it` column and a row for every rule the body states;
   - the open-questions table gains its `Answer` column;
   - the diagram is re-checked against the diagram rule.

   Moving a statement is a layout move, never struck through.
3. **An old-shape guide** (`## How it works` and no `## Who uses it`; an overview with `## The areas`) moves each statement under its new section:
   - a flow → the `### <task>` under the `## For <person>` it belongs to; a system check the person does not notice is dropped;
   - Setup → `## Rules and limits`; How it connects → `## See also`; Who can do what → `## Who uses it`;
   - the end example → the task it illustrates, or `## A <period> in numbers`;
   - inline ids → the stamp comment; inferred purposes → `## Open questions`.

   Wording changes only where the shape demands it.
4. **Retired levels.** A `<name>.behind-the-scenes.md` or `<name>.technical*.md` beside the guide is from the three-level shape: read it as a lead for the update (a person or a screen it names that the guide lacks), then delete it — git keeps its history. The lint's `retired-level` WARN lists every one left.
5. **Add only what the shape needs** — the `Who uses it` table (every role, administrators included), key ideas, `**Where:**` paths and labels, the diagram, callouts, screenshots — from a **targeted** lookup (the UI routes and labels per `feature-trace`'s recipes, the running screen), not a full re-trace.
6. **Re-trace only the code delta** — `git diff <sha>..HEAD` over the area's paths. No delta, no re-trace. A guide whose `**Screenshots:**` line is `pending` and a run given an environment: the capture pass of *Screenshots*, nothing else.
7. **Check it, do not trust it.** Close the update with `doc-lint.py --kept-from <the guide's old sha, or the commit before the update> --dir <folder>`: every `fact-kept` WARN is a number or quoted message the old guide had and the new one has not — restore it, or name in the report the code change that removed it. The `INDEX.md` line is edited into its shape in the same update.

## 4. Verdict every statement

Against the re-trace: **Agrees** · **New** · **Gone** · **Contradicts**.

## 5. Update, don't rewrite

`~~old~~ → new` keeps one generation of history inline and marks a changed **fact**; moving a statement to its new section is a layout move and is never struck through. Re-check the diagram whenever a task, a state or a transition changed; re-run the example's arithmetic whenever a number it uses changed; re-capture the screenshot of every task whose screen or steps changed.

## 6. `Gone` needs care

Say whether the feature was removed or your trace did not find it; never delete a `#confirmed` KB statement on the strength of a failed search.

## 7. `Contradicts` escalates

Present the documented statement, the code's behaviour, and both readings — *stale documentation* vs *code defect*. Never silently pick one.

## 8. Re-stamp

The new sha in the stamp comment, a `Last updated` line and the `Describes` date; log the session in `active-context.md` (KB runs).
