# Feature document standards

A feature is documented as one guide from one trace, `<NNN>-<slug>.md`, for the people who use the product (every role, administrators included) and the analysts and product owner who read along, with a few screenshots in `screenshots/<NNN>-<slug>/`. Apply these when you write or edit one. Severity: **blocker** states what nobody can check or confirmed, **major** weakens the evidence or the reader's grasp, **minor** is form. Where the project consistently does otherwise, follow it. The delivery note a `DOC1` run also writes is outside this file; `doc-business-model`'s delivery-note reference owns its shape.

**The file**

- One guide per feature; no `.behind-the-scenes.md` or `.technical.md` beside it (retired levels: a leftover one is read as a lead, then deleted). *major*
- `## About this document` closes the file and the last line is one stamp comment (`<!-- guide · source: feature-documenter @ <commit> · stories: <ids, when used> · audience: shareable -->`), both shaped in `guide-shape.md`. Internal ids and story ids appear only in the stamp, and the visible block carries no `**Id:**`, `**Owned by:**`, `**Derived from:**`, `**Generated by**`, `**Models:**` or `**Audience:**` line. Never an environment address or login. *major*
- `doc-lint.py --dir <folder>` (in `doc-business-model`'s `scripts/`) exits 0 before handing off; every WARN is fixed or explained. *major*
- When the code moves, update the guide in place: fold answered questions first, re-check what changed, re-stamp, re-run the example, re-capture the screenshots whose task changed. A guide in an earlier shape moves into this one in the same file, `**Created:**` and every fact kept, and `doc-lint.py --kept-from <rev>` shows no unexplained `fact-kept` line. *major*
- `<NNN>` is never renumbered or reused. Nothing is written into `docs/business-model/`; a `#confirmed` entry the code contradicts is escalated. *minor*

**What it says**

- Never invent a purpose. A purpose (why a rule exists) is stated in the body only from a person's answer in `## Open questions`, the stories of the plan that built the feature (`docs/plans/**`, also `implemented/`; the ids go in the stamp's `stories`), or a `#confirmed` KB entry. Anything else is a row in `## Open questions`. Never write a tier tag or `#confirmed`. *blocker*
- An answered question is folded in first: one plain sentence where the rule is stated (and in *Rules and limits* when it changes a row), then its row is removed and its id never reused. An answer the code contradicts is not folded; the report escalates both readings. *major*
- Where code and story disagree, the guide states what the code does; the difference goes to the delivery note and the report. *major*
- Nothing unreachable is written up as a capability. Code wired to a trigger outside the repository (a message nothing in the repo publishes) is documented, with an open question "who starts this?". *major*
- Defects found while tracing go to the run's report, routed to `code-auditor`, never into the guide. Behaviour is stated neutrally: bug, defect, flaw, broken, wrong, mistake, vulnerability and "should have" are lint warnings, quoted product text exempt. *major*
- A timing or delivery guarantee ("exactly once", "immediately", "as soon as", "in real time"…) is written only where the code shows it; a roadmap promise ("not yet", "coming soon") never. *major*

**Shape**

- The section order, the task format, the tables and the stamp are `product:doc-business-model`'s `references/guide-shape.md`, which the `feature-documenter` agent loads. Two bars stay here: every role found, **administrators** included, has its own `## For <role>` section; and a task holds no formula, its outcome pointing to `## How it is calculated`. *major*

**Language**

- Uses the client's own terms from the trace's `Client vocabulary` table and the running screen; a refusal quotes the exact user-facing message. *major*
- Client language only: no class, method, table or column names, file names, status codes, exception types, framework nouns, jargon (endpoint, payload, handler…), tier tags or `file:line`. A word that needs defining is replaced; a client's own technical-sounding word stays only when the product shows it. *major*
- The worked example sits in the task that computes, numeric whenever there is a calculation, threshold, layered setting or time-based process. Every rule number is the code's exact value, the arithmetic is recomputed after any change, and the example never extends past what the code says. *major*

**Screenshots**

- Captured from a running **non-production** environment, signed in with a test login for the task's role, never from production, a mock-up, a design file or memory. Only a person can waive them, and the waiver is recorded in *About this document*. *blocker*
- Screenshots never block the text. With no environment the guide is written in full, holds no image and records `**Screenshots:** pending — <why>`. A later capture run checks every bold label against the screen (the screen wins; a difference is fixed and raised as an open question), captures, and replaces the `pending` line without a new trace. *major*
- At most one per task, only for a task with a `**Where:**` line, six per guide; never one per step. Placed right under that line as `![<what the screen shows, in the client's words>](screenshots/<NNN>-<slug>/<task-slug>.png)`, the alt text never empty. *major*
- Shows the task's screen in the state the task describes, the example's values when it has one, and every label the steps name, spelled the same. Test data only: no real person's data, secret, key, token or internal address. *blocker*
