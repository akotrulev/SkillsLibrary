# Task-block rules by kind of task

Read from `SKILL.md` Step 4 when a task is bound to `fe-react` / `fe-blazor`, when a `be` task adds an entry point, outbound call, background job or business event, when a task is a batch, or when it is a `Q` or `TD` task. The general task block is `plan-format.md` §4.

- **Frontend tasks cite their screens.** A task bound to `fe-react` / `fe-blazor` names the `experience-plan.md` screen ids it delivers (`S3`, `S4`) and the journey it completes (`J1`), lists `design:app-structure` in its skills, and carries `experience-plan.md` §6's responsiveness budget as bullets verbatim. The capability's last task is usually this one, and its deliverable is the journey's behavioural sentence.
- **Web `fe` tasks carry their routes' rendering spec.** The task quotes the §4a `rendering_plan` entries of its routes (mode, cache, server-rendered content, islands, deferred sections) and their `acceptance` budgets, states that it may not change a route's `mode`, and adds to its `Gate:` the build-side checks of `experience-plan/references/rendering-strategy.md` § Verification (no hydration warning, no-JS render, island-only bundle, budgets). The app-shell task also sets the hydration signal the journey tests wait on. The raw-HTML and cache-header tests are the `Q` journey task's, written red before the screens.
- **An implementation task names its signals.** One bullet lists the spans, decision-point logs and metrics it adds: a span per business operation, a log per rejection or state change, a metric per business event with low-cardinality labels. The telemetry base is the foundation's, so the task never rebuilds the SDK, the exporters or the local stack, and the gate's telemetry smoke (`plan-format.md` §5) queries the names the bullets carry.
- **A batch is one task with one deliverable.** Under agent-batched sequencing a task is the whole module or screen area, and its deliverable is the one sentence that covers the set ("every endpoint under `/bookings` implements its documented behaviour and validation", not a list of five). A batch whose deliverable takes two sentences was two batches, and a batch of unrelated leftovers grouped because one agent owns them is a bucket.
- **`TD` tasks write documents, and say so.** A test-plan task's deliverable names the plan files and what each holds ("`docs/test-plans/004-booking-test-plan.md` covers E2: its versions, every included part of US6–US10 in scope, out or deferred, a scenario for every AC, and the Definition of Ready and Done"); a test-case task's names the suites. Both say `Gate: none` with the reason from `plan-format.md` §4. The `Q` task for an epic lists the test-plan task in `Depends on` and automates the `TP-` rows bound to its agent; the last runnable task checks each plan's Definition of Done.
- **Test-first deliverables name the tests.** A `Q` task's deliverable names its tests and their red reason; an implementation task's names the `Q` tests it turns green. Every own-tests command is filtered by file or class and runs only the tests the task wrote plus the `Q` tests bound to its deliverable; the `Q` task's `As built` lists the filter each implementation task uses.
