# Data — Migrations (cross-engine)

Tool selection, repo layout, naming, and online-safe DDL / data change recipes that apply across PostgreSQL / SQL Server / MySQL / MongoDB / DynamoDB / Cosmos DB. Engine-specific syntax lives in the per-DB skills (`data/<db>`).

## When to use

- Picking a migration tool per stack
- Structuring a repo's migration directory
- Authoring an online-safe DDL change (rename, type change, NOT NULL add, drop)
- Backfill planning (batched, idempotent, resumable)
- Coordinating schema changes across services touching the same DB
- Versioning and rollback strategy

## When NOT to use

- Engine-specific schema design → `data/<db>`
- One-off DML in prod — use a script, not a migration

## Tool selection per stack

| Stack | Primary | Secondary | Notes |
|---|---|---|---|
| **.NET 10** (8/9 supported) | EF Core Migrations | DbUp (raw SQL) | EF Core for ORM-tracked schemas; DbUp for environments where you'd rather write the SQL by hand. Version-aware: match the project's TFM, never up-level |
| **Java 21** | **Flyway** | Liquibase | Flyway's plain-SQL files are the easiest to review in PRs; Liquibase's XML/YAML is heavier — pick Flyway unless the team is already on Liquibase |
| **Node 24 (TS)** | Prisma Migrate, Drizzle Kit | `node-pg-migrate`, `umzug` | Prisma is most opinionated; Drizzle Kit when you want lower-level control |
| **MongoDB (Java)** | Mongock | — | Annotated change-sets, locked execution |
| **MongoDB (Node)** | `migrate-mongo` | `mongodb-migrations` | Plain JS migrations with `up` / `down` |
| **MongoDB (.NET)** | hand-rolled idempotent runner | — | Record applied migrations in a `_migrations` collection |
| **DynamoDB / Cosmos DB** | hand-rolled change-feed-driven backfills | — | No native DDL; migrations are dual-write + backfill + cutover |

Pick **one** tool per project and apply it consistently — mixing two (Flyway + EF) is a recipe for drift.

## Repo layout

```
db/
  migrations/
    V20260528_1000__create_orders.sql
    V20260528_1100__add_orders_currency.sql
    V20260529_0900__backfill_orders_currency.sql
    V20260530_1000__set_orders_currency_not_null.sql
```

Naming convention used by Flyway is fine for every other tool too — version-then-description, sortable, traceable. Each file is **one logical change**. A migration that adds a column AND backfills it AND sets NOT NULL is three migrations.

## Universal rules

1. **Forward-only in production.** "Down" scripts are for local dev only — corrective migrations beat down-migrations.
2. **One logical change per migration.** Reviewable, revertable, traceable.
3. **Idempotent where possible.** A migration run twice should not error or corrupt — `CREATE TABLE IF NOT EXISTS`, `INSERT ... ON CONFLICT DO NOTHING`, `WHERE NOT EXISTS`.
4. **Migrations run from the pipeline**, not at app startup. The pipeline has a clear pre-deploy step. App startup migrations race during rolling deploys.
5. **Migrations are reviewable like code.** Plain SQL or simple JS — avoid generated bytecode or XML-heavy diffs.
6. **Schema and data migrations are separate files.** A DDL migration and a backfill DML migration are two PRs / two files even when conceptually one change.

## Expand–contract pattern

The universal pattern for **online-safe** schema evolution under rolling deploys:

```
Phase 1 (Expand)    Phase 2 (Migrate writes)   Phase 3 (Migrate reads)   Phase 4 (Contract)
─────────────────   ────────────────────────   ───────────────────────   ───────────────────
Add new shape       Code writes both old +     Code reads from new       Remove old shape
alongside old.      new. Old is still           shape. Old is dead.       (column / collection /
Nullable.           authoritative.              Verify with metrics.      attribute / table).
```

Each phase is **one release**. Never collapse phases into one release — the rolling deploy will have versions reading from the old shape while another version writes only to the new.

### Common moves under expand–contract

| Move | Phases |
|---|---|
| Add a column (nullable, then NOT NULL) | (1) ADD nullable column → (2) backfill in batches → (3) set NOT NULL after backfill completes |
| Rename a column | (1) Add new column → (2) dual-write both → (3) backfill → (4) switch reads → (5) drop old |
| Change column type | (1) Add new column with new type → (2) dual-write with cast → (3) backfill → (4) switch reads → (5) drop old |
| Split a table | (1) Create new table → (2) dual-write inserts/updates → (3) backfill historical → (4) switch reads → (5) stop dual-write → (6) drop old |
| Merge two tables | Same pattern, reversed |
| Add a non-null FK | (1) Add nullable FK → (2) backfill referenced rows + the FK column → (3) set NOT NULL + add FK constraint |

## Online-safe DDL recipes per engine

These are pointers; engine-specific detail lives in `data/<db>`.

| Operation | PostgreSQL | SQL Server | MySQL | Mongo / Dynamo / Cosmos |
|---|---|---|---|---|
| Add nullable column | Metadata-only | Metadata-only | INSTANT in MySQL 8 if at end of row | Just write |
| Add NOT NULL with default | PG 11+ metadata-only for non-volatile defaults | Literal default = metadata-only | Splittable | n/a |
| Add NOT NULL without default | **Split**: add nullable → backfill → SET NOT NULL | Same | Same | Validator update phase (Mongo) |
| Add index on large table | `CREATE INDEX CONCURRENTLY` | `WITH (ONLINE = ON, RESUMABLE = ON)` (Enterprise / Hyperscale) | `ALGORITHM=INPLACE, LOCK=NONE` or `pt-osc` / `gh-ost` | Online by default (Mongo); GSI add is online for Dynamo; indexing policy edits are online for Cosmos |
| Rename column | Avoid — use expand-contract | Avoid — use expand-contract | Avoid — use expand-contract | Avoid — use expand-contract |
| Drop column | Always after a release where it's no longer read | Same | Same | Drop attribute write |

## Backfill rules

- **Batched** — `UPDATE ... LIMIT 5000` (or DB equivalent), loop, sleep between batches. Never one statement against millions of rows.
- **Resumable** — write the cursor / offset / max-id processed somewhere durable; restart from there
- **Observable** — log `n rows processed, n total, ETA <eta>`
- **Throttleable** — a knob to slow it down if load metrics spike
- **Independent of the schema migration** — schema DDL is one PR / one file; backfill is another. The schema DDL can roll forward without the backfill.

```sql
-- PostgreSQL example
DO $$
DECLARE
    batch_size CONSTANT int := 5000;
    affected int;
BEGIN
    LOOP
        UPDATE orders SET currency = 'EUR'
        WHERE currency IS NULL AND id IN (
            SELECT id FROM orders WHERE currency IS NULL ORDER BY id LIMIT batch_size FOR UPDATE SKIP LOCKED
        );
        GET DIAGNOSTICS affected = ROW_COUNT;
        EXIT WHEN affected = 0;
        PERFORM pg_sleep(0.05);
    END LOOP;
END$$;
```

For long-running backfills, prefer a **dedicated job** (a service, a Lambda, a worker) over an in-migration loop — easier to observe, throttle, and re-run.

## Multi-service coordination

When several services touch the same database (often a sign you should split the database, but real world is messy):

- Coordinate the expand-contract phases via a **shared migration calendar**
- The service that owns the table runs the migration; consumers update their code in lockstep
- Document **read-compat** and **write-compat** ranges explicitly: "After release R-12.4, all writers must include the `currency` field; readers must tolerate absent currency until R-13.0."

## Cosmos / Dynamo / Mongo nuances

NoSQL engines lack `ALTER`. Migration moves:

- **Add attribute** → just write it; old items have nothing; readers tolerate the absence
- **Rename / restructure** → dual-write old + new; backfill via change feed / streams / change stream Lambda; switch reads; remove old
- **Change partition key** (Cosmos / Dynamo) → new container/table + Stream-driven copier + cutover (treat as a rebuild)
- **Tighten Mongo schema validator** → start with `validationAction: warn` during the migration window, then switch to `error`

## Rules

- One logical change per migration file
- Versioned, sortable names (timestamp or sequence)
- Migrations execute in the **CI/CD pipeline** as a pre-deploy step, never on app startup
- Plain SQL or simple JS — avoid heavy abstractions
- Forward-only; corrective migrations
- Backfills batched, resumable, observable
- Schema and data migrations split per file
- Expand-contract across releases; no collapsed phases
- The migration runner has its own DB role with DDL privileges; the app runtime role has DML only
- One migration tool per project — never mix

## What NOT to do

- No app-startup migrations in production
- No DDL + DML in the same migration file
- No `DROP COLUMN` in the same release that stops writing to it
- No `ALTER TABLE ... NOT NULL` on a large table without prior backfill
- No `CREATE INDEX` without the engine's online option (`CONCURRENTLY` / `WITH (ONLINE = ON)` / `ALGORITHM=INPLACE`) on a hot table
- No down-migrations relied on in production
- No "manual SQL run by the DBA" outside the migration tool — every change is auditable
- No backfill run from a developer laptop — pipeline / worker only
- No migration that locks a hot table for the duration of a multi-million-row update
- No migrations PR with > 1 logical change — split it

## Generation steps

1. Identify the change as **schema-only**, **data-only**, or **both**; split into separate files if both.
2. Pick the **expand-contract phase** for the change; what is in this PR vs the next one.
3. Choose the engine-specific online-safe primitive (`CONCURRENTLY`, `INPLACE`, `ALGORITHM=INSTANT`, etc.)
4. Write the migration file in the project's tool's naming convention.
5. If a backfill is needed, write it as a separate file or, for large backfills, as a job that the pipeline triggers post-deploy.
6. Verify locally against a representative dataset; check the execution plan / row count.
