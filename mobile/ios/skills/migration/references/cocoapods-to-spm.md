# CocoaPods → Swift Package Manager — before 2026-12-02

**CocoaPods trunk goes read-only on 2026-12-02** (blog.cocoapods.org/CocoaPods-Specs-Repo — re-read it before a run). After that date no new pod version or new pod can be published to trunk. Existing versions keep resolving, so an app that builds today still builds; what stops is every dependency's future release, security fixes included. A project with a `Podfile` therefore has a dated plan, and a **new** project never gets one (A10).

## 1. Inventory

```bash
ls Podfile Podfile.lock Pods *.xcworkspace 2>/dev/null
rg -n "^\s*pod " Podfile
```

For every pod in `Podfile.lock`, record: pod and version · who uses it (`rg -ln "import <Module>"`) · whether it publishes a `Package.swift` (the pod's repository, or its documentation's "Swift Package Manager" install section) · whether it ships a binary `.xcframework` · whether it contains Objective-C or resources · whether it is a **private** pod from your own spec repo.

| Pod kind | Replacement |
|---|---|
| Publishes SPM | `.package(url:from:)` — the default, and most large SDKs do |
| Binary xcframework only | `.binaryTarget(url:checksum:)` or a vendored `.xcframework` in a local package |
| No SPM, source available | A fork with a `Package.swift`, pinned to a tag — an owned maintenance cost, say so |
| Private pod | Make the repo a package: a `Package.swift` and a tag; Xcode resolves it over the git credentials CI already has |
| A dev-only tool (SwiftLint, SwiftGen) | The tool's release binary or an SPM plugin; remove it from the app's dependency graph |
| Unmaintained, unreplaceable | Keep a `:git =>` pod pinned to a commit as the **last** exception, with an owner and a date; this is a finding, not a plan |

A pod with no replacement and no owner is the real blocker — find it first.

## 2. Move one pod at a time

1. Add the package in Xcode (File → Add Package Dependencies) or in a local package's `Package.swift` — **dependencies live in the local packages that use them**, not on the app target ([`project-setup`](../../project-setup/SKILL.md), B20).
2. Remove the `pod '<Name>'` line; `pod install`.
3. Fix imports (module names sometimes differ), resource lookups (`Bundle.module` for a package's resources), and any `use_frameworks!` linkage assumption — static vs dynamic linking changes symbol visibility and launch time (N8).
4. Build and test; commit **one pod per commit**.

Mixed-language pods become SPM targets with an `include/` directory and, where needed, a module map; resource bundles move to `resources: [.process(…)]`.

## 3. Remove CocoaPods last

When `Podfile` is empty:

```bash
pod deintegrate
git rm -r Podfile Podfile.lock Pods
```

- The project opens as `.xcodeproj` / `.xcworkspace` generated by Xcode — delete the CocoaPods workspace and update CI to build the project, not the workspace.
- Remove `pod install` and the `Pods/` cache from CI; commit `Package.resolved`.
- Delete CocoaPods build phases (`[CP] Embed Pods Frameworks`, `[CP] Check Pods Manifest.lock`) if `deintegrate` left any, and the `Pods-*.xcconfig` includes from the app's xcconfig files.
- Privacy manifests: SDKs that ship a `PrivacyInfo.xcprivacy` carry it through SPM; re-run the privacy report from an archive ([`mobile-shared-store-compliance`](../../../../_shared/store-compliance/SKILL.md)).

## 4. Traps

- **Deleting `Pods/` first** — the build breaks with no baseline to bisect against.
- **Version drift on the swap** — pin the SPM version to the one the lockfile had, then upgrade as its own change.
- **A pod's transitive pods** — each is a row in the inventory.
- **Tuist / XcodeGen projects** — dependencies change in the manifest, not in Xcode (B24).
- **Signing and build phases** that referenced `${PODS_ROOT}`.

## Done

`Podfile` gone; `Package.resolved` committed; CI builds without `pod`; the release archive's size and launch time are within noise of the baseline; audit rows A10, B20, B22 pass.
